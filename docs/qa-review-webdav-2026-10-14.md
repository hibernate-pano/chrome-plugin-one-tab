## 二、测试有效性评估

### 判断：这批测试**部分**能作为迁移安全的证据

1270 个测试全绿是必要条件，但不是充分条件。绿灯不等于覆盖到位——
尤其在 mock 密集的同步/网络层。逐项核查如下。

### 关键路径覆盖矩阵

| 关键路径 | 覆盖情况 | 说明 |
|---|---|---|
| 客户端加解密（Vault） | ✅ 有 | 含格式版本拒绝、salt 不匹配拒绝 |
| 明文哈希稳定性 | ✅ 有 | `stableStringify` 递归排序key |
| 删除熔断判据 | ✅ 有 | 含比例/绝对双阈值、边界值 |
| 远端文件布局 | ✅ 有 | layout 路径生成/解析 |
| 配置校验 | ✅ 有 | 含凭据不落盘断言 |
| **多设备并发写同一group** | ⚠️ 部分 | 有 412 冲突裁决测试，但未见真正的「双设备交错写」场景 |
| **墓碑（tombstone）处理** | ⚠️ 部分 | 有 `encodeTombstone` 单测，端到端删除传播需确认 |
| **last_op_seq 拒绝旧写入** | ⚠️ 部分 | 认输预检有单测，但「久未同步设备覆盖云端」这个 P0 场景建议补端到端 |

| **密钥派生失败 / 解密失败** | ✅ 有 | 统一错误文案有断言 |
| **主机权限申请/拒绝** | ❌ **无** | `permission.ts`(97 行) **零覆盖**（见下） |
| **网络失败（status 0）路径** | ⚠️ 部分 | 传输层有 mock，需确认 mock 是否真实反映浏览器拦截行为 |

### 问题清单

| # | 严重度 | 位置 | 问题 | 建议 |
|---|---|---|---|---|
| 1 | **P1** | `tests/`（缺失） | `permission.ts`(97 行) 零测试：origin 解析、用户拒绝、环境不支持三个分支均未覆盖 | 补 3 个用例，尤其「用户点拒绝」要断言返回 false 而非抛错 |

### 一个方法论提醒

本分支的正确做法是**真机E2E**（`scripts/e2e-webdav-local.mjs`、
`e2e-webdav-permission.mjs`、`webdav-capability-matrix.mjs`），
并留下了「推翻前提」的实测记录。**这是本分支最大的质量优势**——
单元测试用的是 mock，而分支自己已经证明「WebDAV 服务端行为与协议文档不符」，
那么 mock 的可信度天然低于真机。建议继续以真机 E2E 作为最终判据，
单测作为回归网。

## 四、QA 工程师独立复核（第二轮，交叉验证）

QA 独立跑了一遍门禁，结论与我完全一致，并补充了以下我遗漏的发现。

### 4.1 测试可信度的正面证据（比我原先判断更乐观）

- **8 个新文件共 141 个测试全绿**
- **零 `assert.ok(true)`、零空catch** —— 我担心的空洞断言模式不存在
- **`FakeDav` 是有真实条件写语义的内存服务器**，不是随手stub；
  `webdavWiring.test.ts` 跑的是**真实 storage 层**，不是 mock
- 变异验证（人工复核部分）确认两条关键断言是真的：
  - `failsafe` 边界 `>` 改成 `>=` → 4 个用例变红 ✅
  - `compareStamps` 逻辑反转 → adapter 4 个用例变红 ✅

### 4.2 实锤弱点：一条零断言测试

`tests/webdavClient.test.ts:231-235`

```ts
it('204 也算成功（部分服务端不返回 201/200）', async () => {
  const { impl } = makeFetch(() => ({ status: 204 }));
  const client = new WebDavClient(cfg, impl);
  await client.put('x', '{}');   // ← 没有一句assert
});
```

**这条测试只要不抛异常就通过**，等于什么都没验证。若 `put()` 内部把204 当失败抛错，
它会红——但若 `put()` 静默返回错误结果，它照样绿。建议补
`assert.ok(out)` 之类的结果断言。

同一文件 `:218-225` 有一条**值得肯定的测试**：注释明确记录了「这一条曾经就是一条假绿断言」，
并用 `assert.match(err.message, /其他设备修改/)` 钉住了「412 必须提示重新合并」这个
**可据以行动的信息**。作者有意识地防假绿，意识很好。

### 4.3 结构性风险：文本断言测试的固有脆弱性

`syncFailsafeGuard.test.ts:78` 与 `webdavSettingsUi.test.ts:18,22` 用
`readFileSync` 读源码/UI 文本做断言。

**我核实后的判断（比 QA 更乐观一些）**：这批测试**不是**简单的存在性检查。
例如 `syncFailsafeGuard.test.ts:100-110` 断言的是调用点的**实参**是否为 `mergeDropped.length`，
`:118-124` 用的是**否定式断言**（熔断分支内不得出现 `setGroupsImmediate(`）。
注释还记录了作者做过变异验证并因此收紧了断言。

所以风险应准确表述为：
- **「重构即假红」确实存在** —— 改个变量名、挪行、调格式就可能让 `indexOf` 失配
- **「改语义可能假绿」已被作者的变异验证部分抵消**，但换个人重构时容易退化回松断言
- 建议：这类「接线断言」保留（它们能挡住真实的接线回归），
  但**不能替代** `syncEngine` 下载路径的行为测试

### 4.4 QA 的最终判断

> 这批测试是迁移安全的**强证据但非充分证据**，缺permission 覆盖、
> 熔断恢复真实行为测试、多设备并发交错与删改竞态，**P1 补齐后再签字**。

与我 §二 的判断一致。

### 4.5 一条方法论声明（值得记录）

QA 在文件头做了「变异验证」声明，但主动声明其**批量变异脚本有 TAP 并行计数解析 bug，
批量结论已废弃不可信**，只保留人工复核确认的两条。这种「宁可声明自己的验证不可靠，
也不让它冒充证据」的做法，与本分支一贯的诚实度一致，应当肯定。

## 三、总结

- **可以编译、可以构建、1270 测试全绿、体积达标** —— 基本盘扎实
- 测试有效性**中等偏上**：核心算法（加密、熔断、布局）覆盖到位，
  但**权限模块零覆盖**、**并发/墓碑端到端场景偏薄**
- 1270 绿灯**不足以**单独证明「迁移安全」，需配合真机 E2E
- 最高优先级仍是架构报告里的 P1：权限预检未接线
