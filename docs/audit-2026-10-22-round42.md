## 0. 本轮的前提与打法

### 0.1 前提（与 41 轮相同，不再重复推导）

`manifest.json` 的 `action` **没有 `default_popup`** ⇒ 点扩展图标走
`chrome.tabs.create()` 打开一个**普通标签页**。所以：

> **管理页的宽度由用户的浏览器窗口决定（1024 / 1280 / 1440 / 1920 都常见），
> 不是 400px。**

### 0.2 本轮的打法：并行审查 → 主审复核 → 派单 → 收口 → 再审

主审给每位专家**同一个问题**：「就这个产品而言，发挥你所有的毒舌，
找出它的问题，列出来。」五位专家各自独立审，报告落成五份文档；
主审逐条**复核**（不通过的就撤回，见 §5），通过的分派给执行者，
修完再由主审跑门禁 + 真机复验。

**这个打法与前几轮最大的不同**：前几轮是主审自己找、自己修；
本轮是**先有专家报告，再有修复** —— 好处是覆盖面被拉宽了
（架构层与数据安全层在前几轮基本没被系统审过），
代价是要多一道「复核」工序（本轮撤回了若干条，见 §5）。

## 3. 本轮新增的两条能力

### 3.1 「恢复即消费」可撤销（P0-4 / P1-10）—— 本轮的核心

**为什么这是 P0**：1.24.1 定案「点开标签 = 消费掉那条记录；恢复整个会话 =
消费掉整条会话」—— 这是**不可逆的删除**（1.22.0 起无回收站），
而且是本产品**最高频**的两个动作。恢复之后卡片凭空消失，
用户第一反应是「我是不是点错了」，而他**没有任何办法退回去**。
更要命的是**摩擦力分配反了**：删除有确认，恢复（更易误触、更高频）没有。

**语义（已定案，不得擅自反转）**：

- 撤销回滚的是**记录**，不是标签页 —— 恢复动作已经把标签页开在浏览器里了；
  撤销把它们放回列表，**不去关那些窗口**（关掉会让用户更迷惑：标签页明明用着）。
- **锁定会话从不被消费** ⇒ 锁定会话恢复时**不给**撤销按钮
  （挂了就是骗人：按了什么也不会发生）。
- 撤销**同时**撤回那条「让别的设备也删掉它」的删除意图 ——
  否则会出现「本机撤销了、别的设备上却没了」。

**实现分层**：

| 层 | 文件 | 职责 |
|---|---|---|
| 纯函数 | `src/core/consumeUndo.ts` | `applyRestoreConsumed(groups, spec, now, stamp)`：还原的形状、位置、印记 |
| 协议 | `src/core/mutationProtocol.ts` | 新 op `restoreConsumed`（带 `consumedTabs`，支持一次撤多条） |
| SW | `src/background/mutationHandlers.ts` | **先撤删除意图、再写记录**；撤不掉 ⇒ 中止（fail-closed） |
| 存储 | `src/utils/storage.ts` | `retractPendingDeleteIds`：读失败/写失败**都抛** |
| 界面 | `src/components/tabs/useConsumeUndo.ts` | 两个界面共用一条接线（两处各写一遍迟早漂） |
| 文案 | `src/components/tabs/consumeUndoCopy.ts` | 成功 / 已恢复 / 失败的措辞 |

**跨设备正确性靠的是两个结构性事实**（不是「重读队列」那种补丁）：

1. **SW 单写者队列**（`src/background/mutationQueue.ts`）：上传与语义命令串行
   ⇒ 撤销要么整块排在上传之前（意图已撤回 ⇒ 不写墓碑），
   要么整块排在上传之后（墓碑已写 ⇒ 撤销取**更新的印记**把云端行复位）。
   两种顺序都不分叉。
2. **单调 Lamport 印记**（`src/utils/seqRegistry.ts`）：新取的号永远大于
   本机此前发过的任何号 ⇒ 撤销的印记必然新于墓碑。

⚠️ **一个必须记住的陷阱**（写在这里是因为它已经咬过一次）：
端口的 `writtenIds` 在两个后端**含义不同** —— Supabase 只报墓碑 id，
**WebDAV 报的是本轮写上远端的全部 id（含活跃行）**。
所以「队列那一支」**不许**套 `writtenTombstoneIds` 过滤器：
套上去会把「本轮刚写成活跃行」的删除意图误判成「墓碑已写」而跳过
⇒ 云端行刚被写成活跃就再也不会标墓碑 ⇒ **已删会话在别的设备上复活**。
守卫：`tests/guards/consumeUndoWiring.test.ts`（含「队列那一支不许套过滤器」这一条）。

**守卫**：

- `tests/consumeUndo.test.ts` —— 纯函数 + 编排顺序（17 例）；
- `tests/guards/consumeUndoWiring.test.ts` —— 接线级（两个界面都挂了、协议登记了、

**真机验证**（`scripts/lead-verify-undo.mjs`，0 问题）：

### 3.2 会话排序（L-10）

列表的排序此前是**写死**在渲染层的一段表达式
（`createdAt` 倒序），用户**没有任何入口**换 —— 筛选面板给的是三个**筛选**
维度，排序这件事本身被写死了，而且判据埋在组件里，没法单测。

现在判据收敛到 `src/core/sessionSort.ts`（纯函数）：四种排序键
（最近保存 / 最近活动 / 名称 / 会话大小（标签数）），下拉在筛选区一行，
设置项随用户设置同步（新增 migration
`supabase/migrations/20261022120000_add_session_sort_to_user_settings.sql`，
**未在生产库执行** —— 动生产是负责人的决定；客户端有 42703 降级，
迁移执行前后都不阻塞同步）。

两条口径上的诚实：

- **默认键 = `'saved'`**，与旧版写死的表达式在有效时间戳上**逐元素等价**
  ⇒ 存量用户升级后看到的顺序一个都不变（任何别的默认值都是
  「升级即换顺序」）。
- 「最近活动」用的不是字面上的「标签最后访问时间」—— 那个字段在当前数据模型里
  **从来不被更新**，照字面实现会得到一个骗人的选项。
  （标签名也从「最近访问」改成「最近活动」：口径里**改名也算「碰过」**，
  叫「访问」与实际在算的东西对不上。）

⚠️ **这一条差点带着一条假话发版**：判据层、设置层、落盘层全做完了、
守卫也全绿（39 条），但**列表侧根本没接线** —— 下拉能选、顺序不动。
单测守不住这一类（它守的是「排序算得对不对」，不是「排序有没有被用上」），
是收尾阶段对着发版记录逐条核对**实际修法**时才发现的。
现在补了三样：接线守卫（`tests/guards/sessionSortWiring.test.ts`，判据是
「列表喂给 `sortSessions` 的变量 == 列表从 store 读出来的那个变量」）、
真机复验（`scripts/lead-verify-sort.mjs`：四个键逐个换、顺序逐个变、
刷新后还在、0 问题）、以及发版记录里那句「现在可以排序」终于对得上事实。

闸门放在写入端就不需要动协议。

**DS-1 修完之后的已知边界**（写在这儿，免得下一轮重新发现）：
本机归属记录只存在于 `chrome.storage.local`，而**会话本体在 IndexedDB**。

所以这个窗口极窄，但它**不是零**。

## 7. 本轮的元教训（留给下一轮）

1. **真机脚本自己也会骗人。** 第一版撤销验证脚本报了两个「产品缺陷」，
   实际两个都是脚本的 bug（用会话名判标签在不在、按「第几个」定位会话）。
   ⇒ 假阳性必须当场查清是产品错还是脚本错，**不能把结论先写下来再找证据**。
2. **守卫钉死字面量会让「正确的修法」变红。** 本轮又遇到一次：
   `singleOpen.length >= 2` 里 `countSuccessToasts` 返回的是**数字**，
   数字上的 `.length` 是 `undefined` ⇒ 这条守卫**从来没有生效过**
   （把两条成功播报全删掉它也不会红）。修的是守卫，不是实现。
3. **注释里的「为什么」比代码更值钱。** 本轮最有价值的一段代码是
   `syncEngine.ts` 里关于「两个后端的 `writtenIds` 含义不同」的注释 ——
   它是在一次真实的假绿事故里写下来的。没有它，下一个人会把过滤器套回去。
4. **「不可逆的高频动作」必须配一条退路。** 这不是加功能，
   是把**摩擦力分配**摆正：删除有确认、更易误触的恢复却没有。
5. **「判据层全绿」≠「功能被用上了」。** 会话排序那条：判据、设置、落盘
   全做完、39 条守卫全绿，但**列表侧忘了接线** —— 下拉能选、顺序不动。
   判据层守的是「算得对不对」，接线层的问题它**看不见**。
   ⇒ **凡是「有个控件 + 背后有判据」的功能，必须有一条**接线**守卫**，
   而且接线守卫的判据要钉**数据流**（控件读的字段 == 判据吃的那个变量），
   不是钉「两边都出现过这个字段」。
   这条是**对着发版记录逐条核对实际修法**时才发现的 ——
   若不是逐条核对，它会带着「现在可以排序」这句话发出去。
6. **上游的对账必须知道下游拦下了什么。** 账号闸门挡下的会话，
   上游一度当成「已提交」⇒ 用户看不到「还有 N 个没同步」，
   且「本轮是全量」被误判 ⇒ 漏登记的改动可能被当成已补上。
   ⇒ **凡是「本层会拦下东西」的层，都要把「拦下了哪些」透出去**，
   端口类型上写清楚（`blockedAccountIds`）。
7. **审计脚本打印 ✅ 只证明脚本跑完了，不证明画面是对的。**
   本轮两次：`05-confirm-dialog.png` 里其实是一条「无需清理」的 toast
   （演示数据里根本没有重复标签 ⇒ 产品正确地没弹确认框，脚本却照样拍、
   照样打印 ✅），`07-empty.png` 曾经拍的是满列表。同类的还有一次是
   `_shot-options.mjs` 的「自动同步开关应该变成 true」—— 那条断言在
   2026-10-18 的闸门落地后就**一直是错的**（未登录时开不了才是对的），
   于是探针天天报假警，而没人再看它。
   ⇒ **截图/探针脚本必须断言「目标状态存在」再收工**（对话框可见、空态文案
   可见、被闸门挡下时开关保持关闭**且有提示**），并且**闸门改了要回来改断言**。
   一个天天报假警的探针，等于没有探针。

  **它的检测力是实测过的**（6 条变异逐条验过会变红；第一版有**两条零检测力**，
  过程记在守卫文件头 —— 又一次「守卫钉错东西 ⇒ 看起来有保护其实没有」）。
- ⚠️ **这个守卫守不住线上**。线上是 Google 商店的内容，本仓没有它的写权限，
  抓取也不是可靠判据。⇒ **线上漂移只能靠人定期抓公开页核对**（本轮做了，见下）。

## R-43.2 【P0】版本台账说「1.25.1 还在审核队列」，而线上早已是 1.25.1

  不改写历史）；`storeListingClaimGuard` 里加了一条「必须写明发布状态以公开页为准」。

## R-43.3 【P1】读设置会触发一次**全量上传** —— 烧 egress 配额

`src/store/middleware/autoSyncMiddleware.ts:12` 用 `startsWith('settings/')` 判「设置变了」，
而 `loadSettings` 是 `createAsyncThunk('settings/loadSettings')` ⇒
**它的 pending/fulfilled/rejected 三个 action 全都以 `settings/` 开头** ⇒
**每次 `dispatch(loadSettings())` 都排一次 `scheduleUpload`**。

主审实测确认：探针 dispatch 一个 `settings/loadSettings/pending`，中间件确实命中。

**后果链**：`scheduleUpload` ⇒ 置 `pending_upload` ⇒ 3 秒后起一次上传；
`changedGroupIds` 是 undefined ⇒ **没有增量白名单 ⇒ 全量上传**。
而 `dispatch(loadSettings())` 的调用点包括：**每次打开管理页**（`MainApp.tsx:28`，
管理页是全屏标签页不是小 popup）、**每轮后台 alarm 轮询**（`backgroundSync.ts:663`）、
设置页、菜单里的「重新读取设置」。
⇒ **打开一次管理页 = 一次全量上传**。
而 Supabase 的 egress 配额按**出站流量**计费（`backgroundSync.ts:56` 的注释自己就写了
「自动同步每轮都是出站流量，60s 全量轮询是配额见底的主因」）。

**这一条与生产实况直接相关**：主审 2026-10-23 探生产库，
`https://<project>.supabase.co/rest/v1/...` 返回 **402**
（`Service for this project is restricted due to the following violations: exceed_egress_quota`），
`/rest/v1/` 与 `/auth/v1/health` 同样 402 ⇒ **整个项目被限流**（不只是某张表）。
⇒ 配额已经见底，而「打开一次管理页就全量上传一次」正是**加速见底**的行为。

## R-43.4 【P1】服务端不可用时，用户看到的是「请重试」

主审把生产上**真实**的 402 报文喂给 `resolveSyncFailureCopy`（`components/sync/syncPreviewView.tsx:305`），
实测输出：

```
输入: "Service for this project is restricted due to the following violations: exceed_egress_quota. ..."
输出: "上传失败，请重试。若反复出现，请导出诊断信息"
```

三处都不对：
① **「请重试」方向错** —— 服务端项目被封禁，重试一万次也一样；
② **「请导出诊断信息」是甩给用户** —— 诊断信息对用户无用，需要知道这件事的是负责人；
③ **「若反复出现」是废话** —— 它**正在**反复出现。
而且它是纯英文 ⇒ `looksLikeMachineError` 命中「不含 CJK」⇒ 走中文兜底 ⇒
**原始信息（配额被限、这是服务端问题）全丢了** —— 用户完全不知道
「不是我的数据或操作的问题」。

更根本的：`SYNC_REASON_COPY` 登记了一堆原因码（`not_authenticated` / `precheck_unknown` /
`overwrite_empty_cloud_refused` / `failsafe_triggered`…），每条都有一句人话，
**但没有一条覆盖「服务端项目被限制 / 配额超限 / 服务不可用」**。
且错误码在路上**被丢掉了**：`upload.ts:1133` 只在 message 含 `row-level security policy` 时特判，
其余 `throw error` 原样抛出 ⇒ 到 `syncEngine.ts:1621` 的 catch 只剩
`error.message` 字符串 ⇒ **`code` 没了** ⇒ 上层拿不到 402 这个判据。

## R-43.5 【P1】快捷键保存 = 破坏性动作之后**零反馈**

主审核实链：
1. `TabManager.ts:203-211` 保存成功后调 `showNotification`，**没传 `kind`** ⇒
   按实现（`:538-555`）视为 `kind !== 'error'` ⇒ **受 `showNotifications` 开关约束**；
2. `storage.ts:308` `showNotifications: false`（**默认关闭**）⇒ **默认配置下不发**；
3. 快捷键路径**不打开管理页** ⇒ 管理页的 toast 反馈（`Header.tsx:270-275`）这条路上没有。
⇒ **快捷键保存（重度用户的主入口）成功时屏幕上什么都不会出现。**

这与本仓第一性原则「用户按了键没反应必须有一句话解释」是**镜像**：
键按了，世界变了，一句话没有。而用户此刻的问题很具体 ——
**「我刚才那 20 个标签，存到哪了？叫什么名字？」**

⚠️ 修法**不能**简单地把 success 通知改成无条件发 ——
「显示通知提醒默认关闭」是**已拍板的用户偏好**（`storage.ts:308`）。
正解是**工具栏徽标**（`chrome.action.setBadgeText`）：零新权限、零新依赖、
不打扰、就在图标上，且**不依赖那个开关**。

## 2. 主审亲自处理的三处口径更正（本轮不经 subagent）

这三处的共同形状：**代码是对的，文档是错的**，而**没有任何测试会变红**。
⇒ 主审逐条回到代码现场核实，再改文档，最后加一条**钉真相源**的守卫。

### 2.1 「以最后保存的一方为准」（DS-43-18，P1）—— 教了一个不成立的预期

**真相**（`src/core/opStamp.ts:22-26`）：胜负由 `compareStamps` 决定 =
**序号大者赢，序号相同按设备编号字典序**。
而 `src/utils/seqRegistry.ts` 的头注释自己写着：「序号只在同一设备内单调，
**跨设备裸比数值毫无意义**」⇒ **先保存的那台完全可能赢**。

**改掉的四处**：`README.md:8` / `README.md:73` / `CHROMEWEBSTORE.md:480`（Known Issues）
/ `promo-site/index.html:319`，另加三份计划文档与 `src/core/opStampMerge.ts` 的文件头注释。

⚠️ 这条**最坏的一类漂移**：它让用户以为「我后保存的就赢」⇒ 于是放心地并发编辑 ⇒ 然后丢数据。

### 2.2 「导入的会话也按内容命名（和保存时同一套规则）」（DS-43-8，P2）—— 两档都不成立

| 路径 | 真实行为 | 证据 |
|---|---|---|
| **JSON 备份导入** | **保留文件里的会话名**（一个字都不改） | `normalizeTabsData.ts:181` |
| **OneTab 文本导入** | 只实现了保存规则**第一档**（主导域名），取不到时回落到「导入的会话 N」 | `oneTabFormatParser.ts:33-36` |
| （保存路径） | **三档**：域名 → 页面标题 → 时间戳 | `sessionName.ts:269/273/277` |

⇒ 「同一套规则」在 JSON 那档**根本不成立**（它不命名），在 OneTab 那档**只成立 1/3**。

顺带补上了一条此前没人说的：**OneTab 导入的会话一律 `isLocked: false`**
（那个格式里没有这个字段），而 JSON 导入**保留锁定** ⇒ 导入后想防误删要重新锁定。

### 2.3 「删除会同步到其他设备」—— 删除可能被撤销（DS-3，P0 的修法②）

`markCloudGroupsAsDeleted` 的墓碑号 = `max(本机 Lamport 号, 云端那行当时的 seq + 1)`，
而对方离线编辑的号来自**它自己的计数器** ⇒ 两个**互不相关**的计数器裸比数值决定胜负
⇒ **删除可能被撤销**（那台离线编辑的设备若印记更大，它会保留并重新上传这条会话）。
而删除确认框写的是「其他登录设备将同步删除」，README / 商店文案三处**没有一处**覆盖这一档。

⇒ 在 `README.md` 与 `CHROMEWEBSTORE.md` 的 Known Issues 里补了「删除 vs 同时编辑」这一档。

## 4. 本轮的元教训（补第 43 轮那条）

> **「文档与代码不一致」不会让任何测试变红。**
