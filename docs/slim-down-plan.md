# TapStack 瘦身方案：把没用的东西挨个删掉

> 依据：与项目负责人的判断对齐——"这就是一个非常简单的标签管理器页面：把数据保存起来，传到云端，然后同步，兼具一些良好的交互和操作，仅此而已。"
> 结论先行：**负责人是对的，而且我能证明具体超在哪。** 下面全部结论都有 grep/调用链证据，不是感觉。
> 性质：本文档是**提案 + 决策清单**，等拍板后才动手。

---

## 一、先说结论：超的不是"思考"，是"没做完的半成品"

这个项目最致命的问题不是某处写复杂了，而是**有一整套子系统只写不读，然后在它上面又盖了观测层**。

最典型的例子：**Yjs 影子双写（V2 计划）**。它的设计目标写在 `docs/v2-plan.md`，读路径切换（V3）至今没做。所以现在：

- 每次用户点一下，SW 都要新建一个 Y.Doc、**全量回放全部历史 update**、写 6.1 KB 增量、重写整份 Dexie 物化视图（8400 行）；
- 这些数据**没有任何业务代码读取过**。`tapstack-y-v2` 和 `tapstack-y-mv` 两个 IndexedDB 库的唯一消费者是它自己和对账采样；
- 体检实测：IDB 只增不减，重度用户一年可到 **296 MB**，回放成本随使用时长 O(N²) 上涨，直接转成点击延迟。

也就是说：**用户为"一个还没上线的优化方案"持续付费（CPU + 存储 + 延迟），收益是零。**

更荒诞的是它上面还盖了一层"门禁"：`yGate.ts` 374 行的判定逻辑，**零业务消费者**——连那个 308 行的开发者面板（`ShadowGatePanel.tsx`）都没接它（`evaluateShadowGate` 全仓零引用）。为了让"数据采集了但没人看得见"这件事变得可见，又写了 374 行判定 + 308 行面板 + 1074 行诊断导出。

**这才是"一轮一轮做很久"的真正原因：不是核心功能难，是维护一个永远收尾不了的子系统。**

## 三、核心功能该长什么样（我建议的"小而美"基线）

### 3.1 必须保留（这是产品的命）

一句话：**存进来 → 找得到 → 恢复回去 → 跨设备一致。**

- 保存：整窗/单标签/右键/快捷键 → `chrome.tabs` 读取
- 本地存储：IndexedDB（现有 `storage-kv` 567 行够用，不需要 Yjs）
- 搜索/筛选/收藏/重命名/备注/锁定
- 恢复会话（新窗口打开）
- 导入/导出（OneTab 文本 + JSON）
- 登录 + 云同步 + 跨设备找回
- 6 套主题 + 明暗 + 单/双栏（这是产品差异化体验，保留）
- 单写者队列（这个设计是对的，且 1.22.11 刚修好，**不要动**）

### 3.2 可以简化（当前实现重，成本远大于收益）

**A. 合并模型可以更简单。**
现在的"操作印记（opStamp）+ 服务端守卫触发器 + 读回校验三件套 + 写前认输预检"是一套很重的机器。我核实过它的必要性：**它是为了解决"两台设备同时编辑同一组"的冲突**。

但坦白说，对一个标签管理器，两台设备同时编辑同一个会话的概率极低，而这套机器的成本是：90 行核心 + 4 个数据库触发器 + 大量读回校验 + 读放大。

> **我的建议不是现在就砍**，而是分两步：先保住 opStamp（它是纯客户端的 90 行，成本低），**把服务端触发器守卫降级为"不做仲裁、只做版本递增"**（减少 2 个迁移 + 每次 UPDATE 的判定），读回校验保留（它救过命）。这一步能砍掉一半复杂度，且不牺牲用户可见的正确性。
>
> **需要你确认**：你是否真的需要"两台设备同时编辑同一会话也不丢数据"？如果不需要，合并可以再简一档。

**B. 加密可以简化。**
现状：PBKDF2-100k + AES-GCM，密钥派生自 `userId`（公开值）——**等于混淆而非加密**（体检 P1-3），而每组每次同步都要付 100k 次迭代（约 9ms × N 组，1.22.9 刚为此做了并发优化）。

> **我的建议**：既然它不是真 E2E，要么
> - **方案甲（省事）**：**去掉加密**，明确 README/商店文案写"云端传输加密 + 服务端静态加密"，省掉 PBKDF2 和那 2.8s 的派生开销；
> - **方案乙（正确）**：做真 E2EE（口令/恢复码派生），但这是独立大工程。
>
> 对一个小工具，**我倾向方案甲 + 诚实文案**，把 2.8s 还给用户。

**C. 双端实现应该合并。**
`src/web/webApi.ts`（516 行）是同步语义的**第二套手工实现**（扩展端有 `download.ts`/`upload.ts`/`readback.ts` 一整套）。两边语义漂移已经发生过（`scripts` 里那个"统计含已删标签"的 bug 就是例证）。

> **我的建议**：二选一——**要么砍掉网页版**（它不是核心功能，省 1202 行 + 一整套漂移风险），**要么让扩展端复用 web 的实现**。**不要维持现状**。

### 3.3 可以砍掉的功能（我的判断，附理由）

| 功能 | 建议 | 理由 |
|------|------|------|
| **拖拽排序** | 考虑砍 | 只为一个功能引入 1.1 MB 依赖、且当前实现是**坏的**（懒加载被击穿，每次开 popup 同步加载）。换成"上移/下移"按钮或拖拽手柄（原生 HTML5 DnD，约 50 行）成本更低 |
| **网页版 dashboard** | 考虑砍 | 1202 行第二套同步实现 + 长期漂移风险，不是核心 |
| **开发者诊断面板** | 砍 | 308 行，且它自己都没接门禁 |
| **性能测试页** | 砍 | 228 行开发期脚手架 |
| **主题从 6 套减到 3 套** | 考虑 | 6 套主题的 CSS + 迁移逻辑是 `src/styles/`（13 个文件）的主要体量。但这是产品差异化，看你取舍 |

## 四、如果只做一件事：把影子链关掉

**这是投入产出比最高的一步，一行配置就能止血：**

```
src/core/yShadowConfig.ts:22  SHADOW_ROLLOUT_PERCENT = 100  →  0
```

立刻收益：
- 每次点击不再新建 Y.Doc、不再全量回放、不再全量重写 8400 行物化视图 → **点击延迟直接下降**；
- IDB 不再无界增长 → **体检 P0-2 消失**；
- `yjs` / `y-indexeddb` / `dexie` 三个包可以从 `package.json` 移除，**首屏体积和构建时间都降**。

**然后**（另起一次提交）真正删掉 1751 行影子链 + 约 1400 行测试 + 3 个依赖。删完这个项目会轻一大截，而且**没有任何用户可见功能受损**（因为读路径本来就走 blob，从没读过 Y.Doc）。

## 六、我的整体建议

说实话，**你那句"这不就是个标签管理器吗"是对的**。这个项目现在的复杂度主要来自：

1. **一个永远收尾不了的子系统**（影子双写 + 门禁 + 观测，约 3000+ 行，零收益）；
2. **为一个不成立的假设（真 E2E）付了运行时代价**（PBKDF2 × N 组 × 每次同步）；
3. **两套同步实现并存**（扩展 vs 网页版）；
4. **为一个低频场景（双端同时编辑）建了一整套仲裁机器**。

这些不是"想得不够清楚"，而是**"没舍得砍"**。

**如果按我的建议做**（关影子链 + 砍网页版 + 拖拽换原生 + 加密诚实化 + 触发器降级），项目会：
- 少 **5000+ 行**代码、少 4 个大依赖；
- 首屏体积和点击延迟明显下降；
- **用户可见功能一个不少**（除网页版和拖拽这两个"非核心"）；
- 体检报告里那条 P0-2 y-indexeddb **自动消失**。

这才是"小而美"。你说删，我就动手——但上面 5 个决策请先给我方向，我不想替你决定什么该留。
