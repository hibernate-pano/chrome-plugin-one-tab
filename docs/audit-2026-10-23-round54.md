# 第 54 轮审计：2026-10-23（基线 v1.26.1 + 第 53 轮增量下载）

>
> **文档状态：已闭环** —— 用户拍板「做压缩」，本轮两块都落代码并全绿：
> ① **零风险的字段精简**（整表 -14%）；② **压缩后再加密**（整表 -81%）。
>
> 起因：用户追问「可以精简上传下载的数据吗？是不是其中很多都没必要？再看一遍」。
> 第 53 轮解决的是「**下多少行**」（行数），本轮解决的是「**每行多大**」（字节）。

---

## 0. 结论（一句话）

**是，有大量「恒定值」被白写：每条标签多写 3 个恒为 null/false 的字段 =
每条标签 56 B 的纯垃圾（占单条标签明文的 15%）** —— 这部分已零风险修掉（整表 -14%）。
**但真正的大头是「加密在前、压缩在后」的顺序问题**：JSON 里的重复被 AES-GCM
打散成高熵密文 ⇒ 服务器端再 gzip 也救不回来 ⇒ **把 gzip 挪到加密之前，
整表下载 -78%**（这一件要用户拍板，因为它会改存储格式）。

## 1. 字节在哪（100 组 × 10 标签，真实加密管线实测）

测量方式：用仓库**真实**的 `serializeTab` + `encryptData`（PBKDF2-100k →
AES-GCM-256 → base64），线上字节 = `前缀 + base64(salt16 + iv12 + AESGCM(明文字节))`。

| | 线上字节 | 占比 |
|---|---|---|
| 整表下载响应体 | 530.5 KB | 100% |
| 其中 `tabs_data` 密文 | — | **≈93%** |
| 行级元数据（`device_id` + `last_sync` + `user_id`） | 96 B/行 = 9.6 KB | 1.8% |

⇒ **杠杆在 `tabs_data` 里面**，不在元数据列上。

## 2. 已修（零风险）：只写「非默认值」

### 2.1 浪费在哪

`src/core/tabDataCodec.ts` 的 `serializeTab` 给**每一条标签**都写了三个恒定值：

```ts
pinned: tab.pinned,                       // 绝大多数标签是 false
last_op_device: tab.lastOp?.d ?? null,    // 绝大多数标签没有 tab 级印记
last_op_seq: typeof tab.lastOp?.s === 'number' ? tab.lastOp.s : null,
```

实测每条标签明文 372 B（10 标签组），其中 **56 B 是这三个恒定值**。

### 2.2 为什么省略是零风险的

读者只有一个：`deserializeTab`（`src/core/tabDataCodec.ts`），判据是

- `pinned` → `data.pinned ?? false`
- 印记 → `typeof data.last_op_seq === 'number' && data.last_op_device`

**缺省与 `null` / `false` 都落不到这两个判据上 ⇒ 读出来的 `Tab` 逐字相同。**
本文件头部原本就写着「印记缺失 ↔ null（云端 NULL 视为全序最小值）」是同一语义 ——
这次只是让**写侧**也守同一条约定（此前写侧写 null、读侧认缺省，两边各说各的）。

老客户端（已发布的 ≤1.26.1）用的是**同一个判据** ⇒ 旧客户端读新写的行结果相同。
`src/core/tabDataCodec.ts` 里那条「无 stamp 的字段 → lastOp 为 undefined」的老测试
（早于本轮就存在）本身就证明了「缺省 ⇔ 无印记」这条等价关系。

### 2.3 效果

| | 精简前 | 精简后 | |
|---|---|---|---|
| `tabs_data`（10 标签/组） | 5035 B | **4291 B** | -15% |
| 整表下载响应体（100 组） | 530.5 KB | **457.9 KB** | **-14%** |

### 2.4 守卫（做过变异验证）

`tests/tabDataCodec.test.ts`

| 断言 | 钉的是什么 | 变异验证 |
|---|---|---|
| 「无印记的 tab 不写 stamp 键，且与『显式 null』对读者完全等价」 | `deserializeTab(缺省)` 与 `deserializeTab(显式 null)` 必须 `deepEqual` —— **老客户端兼容性的全部依据** | 把 `pinned:false` 写回去 ⇒ **红** |
| 「每条标签的上云字节有上限（≤3260 B/10 条）」 | 出网量的字节预算 —— 谁把恒 null 字段加回来谁红 | 把恒 null 的 stamp 写回去 ⇒ **红** |

⚠️ 为什么不是「断言 `data.last_op_device === null`」：那钉的是**实现细节**，
而这条实现在本轮**就是要改**的；真正不能变的���**读者看到的结果**。

## 3. 已做：压缩后再加密（整表 -81%）

> 用户拍板：**做**。代价是「旧版扩展读不了新写的行」—— 已在本节末尾写清影响面。

### 3.1 根因：顺序错了

当前载荷 = `JSON.stringify(tabs) → AES-GCM → base64`。
JSON 里的重复（10 条标签各重复一遍 key 名、同格式的 ISO 时间、同域名的 favicon）
**全被 AES-GCM 打散成高熵密文** ⇒ **服务器端再 gzip 也救不回来**（密文不可压，
最多回收 base64 的 25%）。

把 gzip 挪到加密**之前**，重复在密文之前就被压掉了：

| | 不压缩 | gzip 前压缩 | |
|---|---|---|---|
| `tabs_data`（10 标签/组） | 4291 B | **635 B** | **-85%** |
| 整表下载响应体（100 组） | 457.9 KB | **100.9 KB** | **-78%** |

按组大小的收益：1 标签 -10%、3 标签 -63%、10 标签 -85%、30 标签 -92%。

### 3.2 两条必须遵守的实现约束

1. **自适应**：空组/极小组压缩后**反而更大**（gzip 头 ~20 B + salt/iv/tag 44 B
   的固定开销）⇒ 必须「压完不比原文小就用原文」，不能一刀切。
2. **必须新前缀**：读端按前缀路由（`ENCRYPTED_V3_Z:` → 解密 → gunzip → JSON.parse；
   V1/V2 原样）⇒ **新版本读旧行完全没问题**。但**旧版扩展读不了新写的行**
   ⇒ 那一组会显示「读不出来」（数据不丢，UI 已有这个提示机制，第 51 轮做的）。
   这是本轮唯一需要产品拍板的地方。

### 3.3 ⚠️ 上传侧的自检：写坏不许上云

`src/utils/supabase/readback.ts:248-251` 的读回校验只读
`id, updated_at, version, last_op_*, is_deleted` —— **不读 `tabs_data`**。
⇒ 一行载荷写坏了（压缩/解压不对称、截断），读回校验**照样绿**，
而用户下次下载才发现那一组读不出来。

**做法**：在**写之前**就地往返一次（`upload.ts`）——
加密完立刻 `decryptData` 解回来，与原文 `JSON.stringify` 逐字比对，
不一致就当这组「加密失败」（进 `encryptionFailedIds`，**不写云端**）⇒ fail-closed。

**为什么不改成「写后回读载荷」**：回读要把 `tabs_data` 整列拉回来，
那份字节**就是这一轮要省掉的出网量** ⇒ 为了验一次而再付一次，方向相反。
本地往返覆盖的是同一类缺陷（我们的编解码不对称），且**零出网**。

### 3.4 兼容影响面（发版文案必须写清）

| | 读旧行（V1/V2） | 读新行（V3） |
|---|---|---|
| **新版本** | ✅ 完全不受影响（V1/V2 分支一字未动） | ✅ |
| **旧版本（≤1.26.1）** | ✅ | ❌ 那一组显示「读不出来」——**数据不丢**（云端行保留、本机副本完好），更新后自然回来 |

「读不出来」的呈现是第 51 轮做的机制（`downloadSkippedGroups`），
不会静默把那一组当成「空组」硬删云端行。

### 3.5 压缩在第 53 轮修完之后还值多少

第 53 轮已把后台同步改成「只回源变更行」⇒ 它本来就不吃字节了。
压缩真正压的是**仍然与库大小成正比**的路径：

| 路径 | 现状 |
|---|---|
| 手动同步的**预览**（`src/services/syncPreviewLoader.ts:53`） | 每点一次同步 = 整库下载一次（500 组 ≈ 2.3 MB → 压缩后 ≈ 0.6 MB） |
| 覆盖上传前的**可读性探测**（`src/utils/supabase/upload.ts:353`） | 整库下载一次 |
| 换设备 / 重装扩展后的**首次全量下载** | 整库下载一次 |

⇒ 这三条路压缩后各降 ~81%。

## 4. 剩下的最大一项（压缩也压不到）：指纹探活

每轮同步都会拉一次指纹（`src/utils/supabase/probe.ts:239`），
列是 `id, updated_at, version, is_deleted, last_op_device, last_op_seq`
—— **不含 `tabs_data`** ⇒ 已经是最小形态，压缩对它无效。

| 库规模 | 指纹/轮 | 30 天（144 轮/天） | 占 5 GB 配额 |
|---|---|---|---|
| 100 组 | 12.7 KB | 55 MB | 1.1% |
| 500 组 | 64 KB | 276 MB | **5.5%** |

⇒ 再压它需要服务端提供一个「云端水位线」单行（改 Supabase schema）
⇒ **项目现在是 402 封禁状态、Supabase MCP 也不可用** ⇒ 本轮做不了。

## 5. 本轮**没有**动的地方（以及为什么）

| 项 | 判断 |
|---|---|
| **窄化下载的 `select`**（去掉 `device_id` / `last_sync` / `user_id`） | 只省 1.8%，但要把 `select *` 改成显式列清单 ⇒ 一旦某个列在老 schema 上不存在，PostgREST 报 **42703 ⇒ 整次下载失败**（比上传失败严重得多，`download.ts:326-330` 有明确注释）。收益不抵风险，**不做**。 |
| **去掉上传里的 `device_id` / `last_sync`** | 它们被 `PROTECTED_UPLOAD_COLUMNS`（`src/utils/supabase/missingColumn.ts:47`）保护，且老 schema 上可能有 NOT NULL 约束 ⇒ 删掉写入可能直接插入失败。**不做**。 |
| **短键名 / epoch 毫秒** | 破坏兼容，且与压缩叠加后只多省 6%（`tabs_data` gzip 后 635 B vs 短键名 663 B）⇒ **不值得单独做**。 |
| **brotli** | 比 gzip 再省 25%，但浏览器**没有**原生 `DecompressionStream('br')` ⇒ 要自带 wasm（几百 KB）⇒ 对一个要压包体的扩展是净亏。**不做**。 |
| **加密本身** | 商店文案承诺了加密；且密钥由 `userId` + 随行 salt 派生，本就是混淆级 ⇒ 去掉加密是隐私倒退。**不做**。 |
| **WebDAV 后端** | 它有自己的 vault（`src/sync-backend/crypto.ts`），且 WebDAV 没有出网配额 ⇒ **不动**（动了只会平白破坏兼容）。 |
