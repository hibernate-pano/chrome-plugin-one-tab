## 0. 三条红线（本轮体检确立，不可协商）

体检的核心发现不是"有 bug"，而是**门禁全绿却仍有数据可用性缺陷**。所以先把红线写死，后面每个批次都拿它验收：

1. **不新增"存得下、回不来"的路径。** 任何进入存储的数据，必须存在一条可恢复它的路径。本轮的 7.2（`file://` / `blob:` 会话永久不可见）就是反例。
2. **不新增静默失败。** 删不掉、传不上、读不出来，必须让用户看得见。反例：`scheduleUpload` 吞掉 `setPendingUpload` 写失败、handler 吞掉删除意图登记失败却回 `ok:true`。
3. **修复必须带反向验证。** 每条修复配回归测试，并临时还原修复确认测试转红（仓库已有此纪律，继续执行）。

## 1. 批次一：v1.22.12 —— 安全 + 把"看不见的会话"修回来

**主题**：用户数据安全与可用性。这一批不做任何 UI/交互/主题改动，纯数据面 + 安全面。

| # | 事项 | 对应体检 | 验收标准 |
|---|------|----------|----------|
| A1 | 收口 `profiles` RLS | P0-1 | 先在 Supabase Dashboard 核实 anon 可达性；再 `DROP POLICY "Anyone can view public profile fields"`（表无人用则整表 DROP）；UPDATE 策略补 `WITH CHECK` 并禁改权益列。验收：以 anon 身份 `select` 返回 0 行 / 403。 |
| A2 | **修掉"存得下、回不来"** | P1-4 / 7.2 | ①保存侧与还原侧共用**同一张**协议表（单一真相源）；②取消"整组跳过"档位，改为**整组进结果 + 标记不可回写**（read-only 恢复）；③新增 meta-test：「不存在可保存但不可还原的协议」；④给已卡住的 `mji8xap0kh82cnj8e0k` / `1744560850772` 一条恢复路径。 |
| A3 | `normalizeTabsData` 补**元素级**归一化 | 7.1 | wrapper/camelCase 载荷恢复后 `created_at` / `last_accessed` / `last_op_*` 不再丢失；`tests/normalizeTabsData.test.ts` 增加元素级字段断言（现在只断言外层形状）。 |
| A4 | 处理 `upload.ts:463-468` 死分支 | 7.1 末段 | 删除，或改为抛错。不允许"下载容忍 wrapper / 上传销毁 wrapper"并存。 |
| A5 | 顺手：`scheduleUpload` 不再吞 `setPendingUpload` 失败 | P2 | 失败上浮到调用方可感知，或至少让删除类路径可感知。 |

**为什么 A2 排在"下一个发版必须带"**：它不是历史遗留，是**活的产线路径**——用户每保存一个以本地文件/PDF 为主的窗口，就会新增一组永久不可见的会话。拖一个版本，受害数据就多一批。

**风险与回滚**
- A1 是**线上库 DDL**：先在 staging 演练，记录 `DROP` 前的策略定义以便回滚。
- A2 放宽入库门会触及安全边界：**必须同时保留渲染/点击门**（`javascript:` / `vbscript:` / `data:` 依旧不可点、不可渲染为 href）。这不是"放松安全"，是把"该不该存储"和"该不该导航"这两件事拆开。
- A2 的 read-only 恢复语义要写进 `download.ts` 注释，替换掉现在那句与实际不符的"这一次同步窗口里看不见"。

## 3. 批次三：v1.23.0 —— 资源增长与同步链路（需要设计，改动面最大）

**主题**：把"随使用时间恶化"的两条曲线压平。这一批**必须先有量化基线再动手**。

| # | 事项 | 对应 | 前置条件 / 验收 |
|---|------|------|------------------|
| C1 | y-indexeddb 无界增长 | P0-2 | **先量化**现网 `tapstack-y-v2` 的真实体积与回放耗时（诊断导出已有 `needsSnapshotCount` 可复用）。然后二选一：<br>**路线甲**：把影子写灰度降到 0 直到 V3 拍板（止血，零风险）；<br>**路线乙**：补真正的压缩（写完主动 `storeState`，或定期整库重建）+ 停掉无条件 order 重写（`ydoc.ts:62-63`）。<br>验收：连续 1000 次 mutation 后 IDB 体积不再单调增长；单次 mutation 增量从 6.1 KB 回落到接近 0.22 KB 量级。 |
| C2 | 每次 mutation 的固定 I/O 链 | P1-1 | 先做**零风险**的一步：后台轮询先探活、命中则跳过全量本地读。再评估 journal（要么实现重放，要么下线）与 Dexie 物化视图增量写。验收：400 组规模下，点击→落盘链路耗时不随数据量平方增长。 |
| C3 | 删除广播批量 UPDATE | P2 | 1000 条墓碑从 50–150s 串行降到可接受量级（批量 RPC 或 `upsert` 语义）。验收：占住单写者队列的时间有上限。 |

**这一批和 V3 的关系**：C1 的债是"影子双写"带来的。如果 V3 决定切读路径，影子写的形态会变，**先做 C1 的路线甲（关掉）比现在投入做压缩更划算**。所以 C1 的做法取决于 D2。

## 4. 需要你拍板的三个决策点（我不替你决定）

这三个不是工程问题，是产品/风险偏好问题，定不下来会卡住批次三：

**D1｜加密定位。** 真 E2EE（Argon2id + 每用户 DEK + 恢复码 UX，中大工程，`rebuild-plan.md:56` 已有方案）？还是把"服务端可见混淆"明确写进 README 与商店文案（低成本，但要接受用户预期落差）？
> 我的建议：**这一版先选文案对齐**（诚实且成本低），把真 E2EE 放进 V3 一起做，而不是单独排期——因为它和 V3 的密钥/存储模型是同一件事。

**D2｜V3 到底做不做、什么时候做。** 现在 `tapstack-y-v2` 这套影子写**只有成本、没有收益**（读路径仍走 blob，压缩从未执行）。V3 不做，影子写就该关掉；V3 要做，才值得投资压缩。
> 我的建议：**给 V3 设一个止损日**。到日未切读，就先关影子写。

**D3｜删除模型要不要一条"second copy"。** 无墓碑模型（删除即物理移除 + 云端 30 天 TTL）是拍板过的，但它把全部完整性压力压在删除广播链路上。上一轮体检的 P1-7 提示过：是否在云侧保留一条业务不可见的延长软删窗口（成本低，能兜住"广播丢失 = 永久丢失"）。
> 我的建议：**先不做**，但把它写进 V2-Backlog 显式记账。等批次一的 A2/A5 落地、删除广播链路的静默失败被堵掉之后，再评估是否需要。

## 5. 明确不做（避免范围蔓延）

- 不做多端实时并发协同编辑（`README` 已声明不承诺，维持）。
- 本计划涉及的所有批次都**不动 UI 交互与主题**（1.22.x 刚做过主题收敛，别叠加变量）。
- 不做大爆炸重写；继续绞杀式演进（`rebuild-plan.md:11` 的 Spec-First 原则）。
- 不为了"报告看起来干净"去做无验收标准的重构。

## 6. 每批次的收尾纪律（沿用仓库既有约定）

1. `pnpm validate` + `pnpm test` 全绿。
2. 每条修复做**反向验证**：临时还原修复，确认对应测试转红。
3. 数据面改动必须跑**双设备 e2e**（现有 e2e 种子最大 20 会话/15 标签，**本批次要把种子提到 60+ 标签、并加入含 `file://` 的会话**——否则 A2 这类缺陷结构上测不出来）。
4. 版本号五处同步（`package.json` / `manifest.json` / `.env.example` / `README.md` / `CHROMEWEBSTORE.md`）。
5. `docs/RELEASE-NOTES.md` 顶部补一节（`tests/releaseNotes.test.ts` 会校验）。
6. 打 tag 并**点名推送** `git push origin vX.Y.Z`。

## 7. 一句话总结这个计划

**先把"用户看得见的数据问题"和"安全泄漏"清干净（批次一、二），再回头处理"用户看不见但一直在涨"的资源问题（批次三），同时等三个产品决策落地。**

体检报告里那条"门禁全绿不等于健康"是这一整套排期的出发点：**我们缺的不是测试数量，是"测试没覆盖到的真实路径"。** 批次一和批次二里那些 meta-test（协议表单源、元素级保真、体积门接线、glob 递归）就是补这个缺口，而不是再加一堆同质的单元测试。
