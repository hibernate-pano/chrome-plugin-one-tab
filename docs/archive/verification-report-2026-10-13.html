01结论先行

先说最要紧的：四个修复本身都是对的，缺陷判断全部成立，没有新的 P0。 门禁 1129 全绿、pnpm validate exit 0。 但验证过程本身抓到了一个真实问题—— 新增的 P0 守卫文件里，那条被注释称为「核心」的端到端用例是假绿。

假绿是怎么发生的

tests/localStorageFallbackFailClosed.test.ts 的第 4 条用例注释写着 「这一条是本文件的核心……只要『读失败 ⇒ 落盘被整表覆盖』这条路还通，这里就会红」。 我按承诺做了变异：把驱动的读侧改回 return null（即 P0 的原始形状）， 期望它变红——它通过了。

根因不是猜测，是探针实测出来的：getGroupsForWrite() 内部先写 storage_version，于是写侧的抛错先命中了断言的正则 /localStorage.*不可用|无法读取/。这条用例测的其实是写侧修复， 而写侧与它声称要守的读侧不变式毫无关系。

已修：断言收紧为只匹配读侧的「无法读取」，并把这段变异验证过程写进注释。 修复后重做同一变异，3 条变红（含这条端到端用例）。

为什么这条比「注释写错」严重：假绿的守卫比没有守卫更危险—— 它会让人以为 P0 的数据丢失路径已经有测试兜底，从而不去想「如果它其实没被守住呢」。 这正是本项目反复强调的「对假绿零容忍」，而它这次出现在我自己上一轮的交付里。

03假绿实录与修复

假绿 端到端「整库覆盖不得发生」用例：靠写侧抛错通过，与读侧无关

承诺：注释原文写「即便有人把驱动改回 fail-open、或给 storage 层加了个兜底把错误吞成 []，只要『读失败 ⇒ 落盘被整表覆盖』这条路还通，这里就会红」。

实测：变异读侧（getItem 改回 return null）后，这条用例依然通过；另外两条驱动契约用例变红。

变异：读侧 return null ↓ 探针打印 getGroupsForWrite() 的真实报错： ↓ 「本地存储（localStorage）不可用：无法写入，已中止本次写入。」 ← 写侧，不是读侧 ↓ 断言正则 /localStorage.*不可用|无法读取/ 命中写侧消息 ⇒ 误判为通过

根因：getGroupsForWrite() 内部先调 ensureVersion() 写 storage_version，写侧抛错发生在读之前。而断言的正则同时覆盖了读、写两种消息，无法区分。

修复：把端到端断言收紧为只认读侧的「无法读取」，写侧报错不再算通过。修复后重做同一变异 → 3 条红。

附带价值：注释里补上了这次变异验证的完整过程与它的教训，作为项目知识资产保留。

06遗留观察项（非缺陷）

以下三条是本轮验证中注意到、但经核实不构成缺陷的现象，记录下来以备后续参考， 不是待修清单。

现象核实结论
P1 的 autoSyncConfigReadFailed 是模块级标记，理论上两条并发 readAutoSyncConfig()（setup 异步段 + SW 消息 listener）可能互相覆盖 探针实测当前不会串味：所有消费点都在 await 返回后同步读标记，而两次读的 settle 不重叠。属隐式依赖，非当前缺陷；将来若引入并发读需重新评估
getPendingUpload 从第二个 Promise.all 移到第一个（requestSwPerfFlush 之前） 核实 kvGet 不做进程缓冲 flush（只有 perfSpan 的 read 会），移动不引入读值回归
storage.ts 注释「与 getPendingUpload 在同一个 Promise.all」 该表述正确——指 syncEngine.ts:301 的 getLastUploadTime + hasPendingUpload，本次改动未破坏它。本轮一度误判为陈旧，核实后撤回该怀疑
本轮的一条元教训：除了「改坏实现看测试红」这类变异验证，「把自己的怀疑也拿去变异」同样有效—— 假绿用例和一处误判注释都是在「认真质疑上一轮结论」的过程中被抓住的，而不是靠重跑全绿测试。
