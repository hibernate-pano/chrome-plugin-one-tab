01结论先行

先说好消息，因为它是真的：这一轮没有任何一位专家推翻过既有架构。 历史上最贵的几类缺陷——跨 realm 单写者失效、静默空读固化、分页丢数据、水位单调性—— 都已有可执行守卫钉死，且经得起变异验证。

但 1117 全绿掩盖了三类问题，其中两类会真丢数据

第一类：不变式只做了一半。 indexedDbClient.getItem 早已改成 fail-closed，但 localStorageFallback.getItem 从项目第一天起就是 fail-open，而 pickBackend() 让它一直是可达路径。 两个 P0 都属于这一类：它们不是「守卫失效」，是「守卫从没覆盖到那条路」。

第二类：守卫守的是 1.22 的契约，而 1.23.0 改了产品行为。 自动同步默认关闭是一次行为契约变更，却只改了 changelog 行。README、商店 listing、 新手引导、权限理由、隐私政策五处文案全部停在旧契约上， 而 docsAlignment.test.ts 里没有任何一条断言涉及 自动同步 / syncEnabled / 60s——所以漂移一片全绿。 UX 专家本轮 3 个 P0 全部落在这一类。

第三类：探测与判定的工具本身会假绿。 anon-rls-probe.mjs 把 HTTP 402 判成「✓ 安全」； migrationReplay.pg 的 golden 双库比对在「守卫永远跳过」时恒真。 这两个工具都是用来回答「线上安全吗」的——它们在服务异常时会给出与安全完全相同的绿色输出。

一个必须记住的正面结论：安全专家这次拿到了 supabase db query --linked 的只读访问， 线上实测推翻了上一轮报告的三条 P0——三张浏览历史表 RLS 确实已启用、 profiles 的 USING(true) 已消失、purge 函数对 anon 已无 EXECUTE。 仓库里的「上一轮报告」在这一点上是错的，这一轮有直接证据。

02P0 · 会真丢数据

两条独立验证过的路径。共同特征：读失败被当成「没有数据」，然后整库覆盖，界面报成功，且没有回收站。

P0 localStorage 回退驱动是 fail-open：一次存储不可用可把全部会话覆盖成一条，且回报成功

现象：用户所有会话消失，列表只剩刚保存的那一条，全程没有任何报错。v1.22.0 起无回收站，找不回来。

localStorage 整体不可用（配额满 / 隐私模式 / 站点数据被清） ↓ localStorageFallback.getItem → 探测失败 return null ↓ storage.ts:272 把 null 判成「键不存在」→ 返回 []（不抛错） ↓ getGroupsForWrite() 不抛错（它只 flush + 失效缓存） ↓ applySaveGroup([], newGroup) ↓ setGroupsImmediate 真写成功 → 磁盘被整表覆盖，UI 报「已保存」

根因：fail-closed 不变式只做在 IndexedDB 驱动上，没有做在驱动选择上。 localStorageFallback.ts:16 从初始提交起就是 fail-open，此后所有 fail-closed 收口 （storageFailClosed、localStorageFreshness）测的都是 IndexedDB 桩， 从没测过这个回退驱动。而 storageAdapter.ts:12 的 pickBackend() 让它一直可达。

主线程独立验证：我用真实模块跑了探针——

available(before) = true
available(after)= false
getItem -> null   ← fail-OPEN：读错误长得和「没有数据」一模一样
setItem resolved without throwing  ← 写路径同样静默 no-op（谎报成功）
附带发现：setItem / removeItem 在存储不可用时是静默 return， 调用方以为写成功了。这本身就是「谎报成功」，与读侧 fail-open 是同一根因的两面。

修法：方向 fail-open → fail-closed。getItem 探测失败时抛错 （与 indexedDbClient.getItem 同口径），写侧同样抛错而非静默 return。 更根本的做法是让 pickBackend 在两个后端都不可用时拒绝初始化并出声， 而不是降级到最弱的存储。

变异验证：把该行改成 throw 后全套 9 个测试转红—— 说明这个改动会被既有网接住，新写行为测试时可用同样手法确认。

P0 设置水合门禁漏掉 pending 窗口：冷启动那一瞬改任何设置，会把出厂默认值整份写盘

现象：用户双栏变单栏、主题被改回 legacy、1.23.0 新加的同步档位被重置，全程无提示。若随后手动上传，默认值会扩散到其它设备。

冷启动 → loadSettings 仍在途（IndexedDB 冷读 / 死句柄看门狗 5s） ↓ settingsSlice.ts:24 let settingsReadFailed = false ← 初值「没失败过」 ↓ 用户点任意设置项 → dispatchSaveSettings ↓ settingsSlice.ts:53 判 if (settingsReadFailed) = false → 放行 ↓ storage.setSettings(DEFAULT_SETTINGS 全量) 整份覆盖真实设置

根因：门禁的语义是「读到过真值吗」，实现却建模成「读过失败吗」（只在 catch 置位）。 这两者之间有一段 pending 真空——而它恰好是 IndexedDB 冷启动的常态窗口，不是边缘情况。

为什么它特别难被发现：既有的 noSilentFalseSuccess.test.ts:443 验证了「置位」与「检查」两个环节， 但没有验证初值。变异测试证明了这一点：把初值改成 true（等价于「永远拒绝写」） 后，全套 1117 个测试依然全绿——这说明该场景不是「守卫漏网」，而是压根没有守卫。两者修法不同。

修法（两个方向，需拍板）：

推荐 (b)saveSettings 改成「先读真值 → 合并 → 写」，不依赖 Redux state。用户意图永不丢，且符合本仓「读-改-写一律走真值」的既有纪律。
(a) 三态标记标记建模为 pending / ok / failed，非 ok 一律拒绝写。语义最准，但冷启动那一瞬所有设置项「点不动」。

03P1 · 违反不变式 / 已造成错误

按「是否已经造成用户可见的错误」排序，不按修复难度排序。

P1 · 线上已实测 authenticated 可自助提权：改自己的 plan / subscription_status / stripe_customer_id

这是本轮唯一一个已在线上实测确认的安全问题，也是唯一一条连评审员都可能追问的。

检查项线上实测值应然
profiles 表级 ACLauthenticated=ardDxt（含 UPDATE）应剔除 w
UPDATE 策略 WITH CHECK(auth.uid()) = id只约束了 id
列级 UPDATE 授权plan / subscription_status / subscription_id / stripe_customer_id 对 authenticated 全部可写应全部 REVOKE
客户端是否依赖src/ 零引用 profiles（rg + python 双复核）收紧零业务影响

为什么成立：策略的 WITH CHECK 只验证 id = auth.uid()， 而表级 GRANT UPDATE 覆盖了整张表的所有列。于是任何登录用户都能 UPDATE profiles SET plan='pro', subscription_status='active' WHERE id=auth.uid()。 当前客户端不读这些列，所以现在没有业务影响——但这是一个等着被踩的地雷。

修法已经写好了：docs/fix-profiles-rls-urgent.sql:141-165 里有正确的收口块， 而且注释记录了一个真实踩坑：「表级 GRANT UPDATE 会覆盖列级 REVOKE」—— 必须先 REVOKE UPDATE ON profiles FROM authenticated 再逐列 REVOKE，顺序反了无效。 建议直接从 docs/ 提升为正式迁移：它现在躺在文档目录，没有任何门禁会在它没执行时报警。
P1 最贵的不可逆动作，挂在一个名字叫「打开管理器」的快捷键上

现象：用户按 Ctrl+Shift+S（登记名「Open tab manager」）， 预期只是把管理页调出来看看。实际发生的是：保存整个窗口为会话 + 关闭全部标签 + 新开 chrome://newtab + 打开管理页。

主线程独立验证：

为什么这是 P1 而不是 P3：这是本产品最贵的一次不可逆动作（剪切整窗）， 挂在了一个动机完全不同的入口上。用户按它的理由是「我想看看我存了什么」， 而且快捷键的名字里没有「保存」二字——他甚至不会意识到刚才发生了一次保存。 标签关掉后，他唯一的后悔药是「从刚建的会话里恢复」，而那正是这条快捷键刚替他做的决定。

附带发现：service-worker.ts 里的 case '_execute_action' 是不可达代码——Chrome 文档明文说这类命令「不派发 command.onCommand 事件」。两处行为分叉。

这是产品取舍，不是我能替你定的：二选一—— (a) 改文案承认它是保存动作（与 default_title 拉齐）； (b) 把快捷键重新分配给真正的「打开管理器」，另给保存一个名字里带「保存」的键。 我倾向 (a)：改文案零风险，而 (b) 会改变用户已经记住的肌肉记忆。
P1 读一次设置就凭空调度一次上传：自动同步已默认关闭，打开页面仍出网

架构专家用探针实测：3 条 settings action → 3 次 SYNC scheduleUpload。

// src/store/middleware/autoSyncMiddleware.ts
if (typeof a.type === 'string' && !a.error && a.type.startsWith('settings/')) {
  void sendSyncCommand('scheduleUpload', { delayMs: 3000 });
}

前缀匹配把「读设置」（loadSettings/pending、/fulfilled） 也当成了「本地有改动」。触发点是 MainApp.tsx:26 与 ThemeContext.tsx:57—— 也就是说每次打开页面都会凭空调度一次上传。

两条后果，第二条才致命：
① 自动同步已默认关闭，但打开页面仍创建上传 alarm 并出一次网——与 1.23.0 的产品承诺直接冲突。
② upload() 结尾无条件写 last_upload_time， 于是打开页面后 35 秒内点「手动同步」会被 recent_upload_guard 挡掉， 界面显示「刚完成上传，云端已是最新状态，无需下载」——而用户明明是想拉取别人的改动。
（我已独立复核这条链路：SyncButton.tsx:313 的 REASON_COPY 确实把它渲染成这句话。）

修法：判据从「前缀」改成显式白名单——只认真正改了设置并落盘的 action。改动约 1 行谓词 + 1 条守卫测试。

P1 读失败时日志承诺「下轮重试」，实现却清掉了 alarm —— 同步停摆到下一次 SW 唤醒（修复后 1 分钟自愈）

现象：用户明确开启了自动同步并选了 1 小时，某次网络抖动后同步停摆—— 直到扩展恰好因别的事件被唤醒才可能恢复（无事件就无唤醒，时长不可控），期间没有任何 UI 提示。

alarm 触发 → kvGet(SETTINGS) 抛错 ↓ backgroundSync.ts:163 日志写「按关闭处理，下轮重试」 ↓ backgroundSync.ts:298 chrome.alarms.clear(SYNC_ALARM) → return ↓ 没有 alarm ⇒ 没有确定性的下一轮。重建依赖下一次 SW 唤醒 （service-worker.ts:184 模块顶层会重进 setupBackgroundSync；无事件就无唤醒，时长不可控）

根因：把「读失败」与「用户关掉了」映射进同一个分支， 而两者需要的收尾动作正好相反——用户关闭该停，读失败该重排一个短延迟再试。

探针实测：cleared = ["tapstack-background-sync"]，本轮未重建。

修法：fail-closed 方向不变（不出流量仍然正确），但分两个出口： 读失败时 rescheduleAlarm(1, cfg.intervalMinutes) 而不是 clear； 只有真读到 cfg.enabled === false 才清。日志也要把两者分开—— 现在它们打同一句「自动同步已关闭」，排障会直接跑偏。

P1 「同步策略」展示给用户，但合并引擎从来不读它

SyncButton.tsx:565 用 getSyncStrategyLabel 把 「本地优先 / 云端优先 / 检测冲突后询问 / 较新版本优先」渲染给用户。 但 downloadAndMerge 走的是 mergeOpStamped 无条件 LWW， 全仓没有一处把 syncStrategy 喂给合并决策。

用户选了「云端优先」而实际行为是「较新优先」——这是谎报，而且违反本仓核心纪律： 行为必须出声、不得谎报。deleteStrategy 更彻底：零消费者。

修法（我建议前者）：① 诚实化——删掉那行展示，把 syncStrategy 标 @deprecated，保留上云字段仅为兼容旧数据。 ② 彻底——让合并真的按策略走，但那是重开合并语义的产品决策， 而整组 LWW 是你此前拍板过的模型，不建议在没有重新定义「本地优先」在无墓碑模型下是什么意思之前动。

P1 恢复会话时收不到回包 = 完全静默，而记录已经被删除了

形状：三处恢复路径（TabGroup.tsx:245、 SearchResultList.tsx:248 与 :345）都长这样：

(res: unknown) => {
  const r = res as {...} | undefined;
  if (r && r.success === false) { showDeleteError(...); return; }
  if (r && typeof r.skippedUnopenable === 'number') { ... }
}

r && 这个守卫把「没收到回包」和「收到回包且成功」当成了同一件事。 前者是通道断了（SW 被回收 / 扩展重载），后者是成功——两者对用户的意义完全相反。

后果：恢复流程是 dispatch(deleteGroup) 先跑、50ms 后才 sendMessage(OPEN_TABS)。若此时 SW 已死，用户得到的是： 列表少了一张卡、浏览器没有新窗口、零 toast、零通知。而记录已经物理删除。

这是本仓已知模式，只是这三处漏了：SearchResultList.tsx:278 的单标签打开路径加了 .catch；Header.tsx:185 与 TabList.tsx:49 的保存路径都查了 response?.success。修法照抄它们即可：先判「没有回包」，并把「原会话已从列表移除」无条件说出来。
