## 0. 本轮最重要的一条：一个会让扩展直接不可用的 P0

### A-17 · P0 · `chrome.contextMenus.onShown` 在 Chrome 上不存在 —— service worker 会直接崩

- **位置**：`src/service-worker.ts` 的 `chrome.contextMenus.onShown.addListener(...)`
- **来源**：第一轮 A-12（右键菜单扩到网页上下文）的实施过程中引入
- **事实核查**（我亲自做了三件事）：
  1. Chrome 官方 `contextMenus` 文档的 Events 段**只有 `onClicked`**，
     `onShown` / `onHidden` 一次都没出现；
  2. `onShown` / `onHidden` 是 **Firefox `browser.menus` 专属**事件
     （MDN `menus` API 页面把三个事件列为 Firefox 的，Firefox 的 `contextMenus`
     只是 `menus` 的别名）；
  3. 仓库的 `@types/chrome@0.0.262` 里**也没有** `contextMenus.onShown`
     （只有 `panel.onShown` / `sidebarPane.onShown`，无关）。
- **后果**：`chrome.contextMenus.onShown` 在 Chrome 上是 `undefined`
  ⇒ `addListener` 抛 `TypeError` ⇒ **service worker 在初始化时炸掉**
  ⇒ 整个扩展的所有后台能力（保存、上下文菜单、同步、alarms）全部失效。
  这比「菜单项不会置灰」严重两个量级。
- **为什么会漏**：实施 A-12 时为了「菜单弹出前就把『保存其他标签』置灰」
  选了一个**看起来更优雅**的 API —— 但它不存在。
  `chrome.contextMenus.update(id, {enabled})` 在 Chrome 里完全可用，
  配合 `chrome.tabs.onActivated` / `onCreated` / `onRemoved` 就能达到同样效果。
- **教训（比这一条 bug 本身更重要）**：
  **「文档里没有的 API」不能靠类型检查发现** —— 因为 `chrome` 全局是 `any` 风格的
  未声明成员访问，TS 不报错。必须**去官方文档查**，或者用一个**会崩的**真实路径去试。
  本轮把它变成了一条**类型层面的守卫测试**（断言 `service-worker.ts` 里不出现
  `contextMenus.onShown`），让这条坑不会再踩第二次。

### A-18 · P1 · `contexts: ['page', 'tab']` 里的 `'tab'` 在类型定义里不存在（但运行时合法）

- **事实**：`@types/chrome@0.0.262` 的 `ContextType` 枚举缺 `'tab'`；
  但 **Chrome 运行时是支持的** —— 官方文档的 ContextType 枚举里有
  `"tab"`（"Applies to the context menu of a tab in the tab strip"）。
  是**类型定义滞后**，不是 API 不存在。
- **处置**：保留 `'tab'`（右键标签栏上的标签标题正是用户最想「收起来」的位置，
  删了这个能力就没了），用**精确的类型断言**绕过，并在注释里写明
  「`@types/chrome` 还没跟上 Chrome 运行时」。**不用 `as any`**。

## 2. 本轮新发现

### 2.1 A-5 的完整修法：筛选器不仅要从 UI 里藏起来，**条件也必须一并作废**

第一轮的修法只做了「不渲染这个 select」。本轮复核时发现**漏了一半**：

- 设置页在**另一个标签页**里 —— 本页会收到 storage 变更
  ⇒ 用户可能「开启过固定标签筛选 → 设了条件 → 再关掉设置」
- 此时 select 已经藏了，但**筛选条件仍在生效** ⇒
  用户**看不到筛选项，却被它筛掉了结果**
- 这是最坏的一种隐形行为：比「控件是摆设」更糟，因为**用户无法解释自己为什么搜不到**
- **修法**：条件与 UI 由**同一个开关**决定
  （`resolveEffectiveSearchFilters(filters, collectPinnedTabs)`），
  并让 `activeFilterCount` 与埋点口径同步跟着走
  —— 否则「清空筛选后重试」这个按钮的计数也会说谎。

### 2.4 A-20 · P1 · OneTab 往返会**静默损坏**网址与标题【已实测复现，已修】

这一条是四个 agent 并发改代码的间隙里，我独立审查**导入导出链路**时
**跑出来的**（不是读代码猜的）。

- **实测**：
  ```
  导出：https://ex.com/a|b?q=1|2 | 标题 | 带竖线
  导回：url   = https://ex.com/a          ← URL 被截断
        title = "b?q=1|2 | 标题 | 带竖线"  ← 标题被错位
  ```
- **根因**：OneTab 行格式 `URL | 标题` 天生有歧义 —— 分隔符 `|` **既可能
  在 URL 里、也可能在标题里**。旧实现切**第一个** `|`（2026-10-06 为修
  「标题里的 | 被切开」而加）⇒ 反过来把 **URL 截断**了。
- **为什么 URL 里会有 `|`**：`|` 在 RFC 3986 里**不是**合法 URI 字符，
  但 **Chrome 地址栏不编码它**（`new URL('https://x.com/a|b').href` 原样保留）
  ⇒ `?q=foo|bar`（GitHub 代码搜索的正例）能原封不动存进会话。
  ⇒ 导出即损坏 ⇒ **用户存的标签页变成一个打不开的地址，且无任何提示**。
- **同源另两条**（均实测复现）：标题含**换行** ⇒ 一条标签被拆成两条、
  标题被截断；标题为**空** ⇒ **整行被丢弃** ⇒ 一条合法 URL 消失。
- **修法**：切分判据收成**一条规则** —— **从后往前**找第一个
  「左半边是*无空白的*合法 URL」的竖线。判据依据见
  `docs/RELEASE-NOTES.md` 的「九之二」一节。
- **顺带**：导入的会话改用**域名命名**（与保存路径同一把尺子），
  不再一律叫「导入的会话 N」。
- **新增守卫** `tests/guards/oneTabRoundTripFidelity.test.ts`（23 条断言，
  变异验证 15/15 全部变红再还原）。

### 3.1 D-2 · P0 · version 守卫与印记全序互相打架 ⇒ 后保存的一方被静默吞写【已实测确认，已派修】

- **证据（我亲自在真库上跑的）**：
  ```
  初始行（设备 A 改了 3 次后的云端状态）：version=4, last_op_seq=5000, device='devA'
  设备 B 离线期间改了 1 次：version=2（更小），seq=5001（更大 ⇒ 更晚保存）
  → UPDATE 0 行 → 行状态 4|5000|devA
  → B 的编辑内容落库了吗：否 —— 被 version 守卫吞掉
  ```
  **B 的 seq 更大（= 更晚保存）却输了。**
- **两条守卫在同时起作用**：
  1. `20260826064109` 的 `guard_tab_group_version()`：`NEW.version < OLD.version → RETURN NULL`
     （整行静默丢弃，HTTP 200、无 error）
  2. `20260913132832` 的 `guard_tab_group_op_stamp()`：按 seq → device 全序裁决
     —— 这才是仓库认定的**唯一**裁决规则
  `version` 在 `src/types/tab.ts:71-72` 早已被标注「不再用于冲突裁决」，
  **但数据库守卫仍在用它做第二套裁决，且矛盾时被吞写的那一套赢。**
- **后果链**：`readback.ts:53-56` 的 `isSupersededByCloud` 只看 `row.version > expect.version`
  ⇒ 把「被静默吞写」误判成「合法取代」⇒ 不计为失败 ⇒ 上传返回成功
  ⇒ `setPendingUpload(false)` + 水位推进 ⇒ **该组此后再也不会上行**
  ⇒ 用户看不到任何异常，但**另一台设备永远收不到这次编辑**；
  一旦本地这台被清数据/换机，这次编辑**永久丢失**。
- **承诺冲突**：README:71 / `docs/v2-plan.md:119` 承诺「以最后保存的一方为准」「后保存方整组赢」。
- **根因**：**两套裁决规则并存**。修法是让印记成为唯一裁决源，version 退化成「无印记时的兜底」。

### 3.2 D-1 · P0 · WebDAV 的 manifest 是唯一索引，「manifest 不存在」被当成「远端是空库」【代码复核确认，已派修】

- `adapter.ts:203-222`：`loadManifest()` 对 404/409 ⇒ `return null`（注释：「远端还没有这个库，**合法状态**」），
  而**解析不了** ⇒ `throw`（中止同步）
  ⇒ **「文件不存在」选了破坏性方向，「文件坏了」选了安全方向** ——
  **缺文件比坏文件更危险，代码把它们分在了两个方向上。**
- 触发链：manifest 丢失（第三方同步客户端冲突 / 用户整理目录 / 上一次「分片 PUT 成功 + manifest PUT 失败」的残留）
  ⇒ `firstSync=true` ⇒ 全量上传本机子集 ⇒ manifest 被整体替换
  ⇒ **只存在于分片、不在 manifest 里的会话从此所有设备都看不见**
  ⇒ 更糟：其它设备的水位线认为它们「已上传」⇒ 永远跳过 ⇒ **云端侧永久丢失**
- **承诺是假的**：`layout.ts:34-37` 明写「manifest 是派生数据，全部信息都能通过列出 groups/ 目录重建」
  —— 但**全仓没有列目录的能力**（`client.ts` 只有 `Depth: 0` 的 PROPFIND，**没有 Depth:1**）。
- **修法**：区分「远端确实为空」/「manifest 丢了但分片还在」/「manifest 坏了」三种状态；
  补 Depth:1 列目录能力做索引重建；重建失败 ⇒ **中止本轮（fail-closed）**，绝不按空库处理。

## 4. 已知问题，本轮**明确不做**（记下来，别忘）

### 4.1 撤销删除 / 回收站 —— 推迟到 V2

第一轮 §3.3 的调研结论成立：云端「取消删除」的路径**已经存在**
（`src/utils/supabase/upload.ts:773` 写 `is_deleted=false`），
唯一真实的技术风险是**印记必须严格大于云端墓碑**。

**推迟的理由**（不是「难」，是「现在做错代价比不做大」）：
- 删除语义是本仓**最敏感的一条线**：14 个回归测试 + 4 层文档承诺围着它
  （隐私政策 / 商店 listing / README / `assert.match(en, /no undo/i)`）
- 本轮的核心主题是**「声明 = 行为」**。撤销会新增一层「撤销窗口结束后物理消失」
  的语义 —— 那正是**又一层新的声明**，必须连带改 4 处承诺
- 在诚实性缺口还没补完时动它，是拿「有趣的功能」换「地基稳固」

**V2 的做法（已想清楚，届时直接做）**：本地墓碑 + `is_deleted=false` 的云端反向戳，
窗口 30 天；「撤销窗口结束后物理消失」要**四处同步改**。

### 4.2 卡片级虚拟化 —— 推迟

主列表现在是「会话卡片全渲染 + 标签行按视口懒渲染」。
400 会话时卡片本身有 400 个 DOM 节点（不是 91311），
**卡在 400 个节点的量级不算问题** —— 与 A-11 的 91311 差两个数量级。
真正的瓶颈在标签行那一层，而那一层已经有虚拟化。

**判断**：现在做卡片级虚拟化是**过早优化**，
而且它会引入「拖拽跨卡片时的落点计算」这类真 bug 的风险。
**先不做，等实测数据说话。**
