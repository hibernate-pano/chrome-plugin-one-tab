## 0. 一页纸结论（给不想读全文的人）

**可以做，技术上没有拦路虎，但「Web3 存储」这个说法需要先纠正。**

1. **「Web3 存储」在今天没有可用的成熟方案。** 去中心化存储（IPFS / Arweave / Filecoin）
   现在的状态是：要么自建网关（= 还是要自己运维，和 Supabase 一样），
   要么依赖第三方公共网关（**你的标签页 URL 就是你的浏览历史，交给第三方网关等于
   把最敏感的数据放在别人手里**）。这不是「更私密」，这是「更不私密且更不可靠」。
   → **本方案用「自带存储（BYOK）」这个词，不叫 Web3。**详见 §2。
2. **你要的三个收益，WebDAV 都能拿到，且是本项目最现实的一条路。**
   你的存储费用归零、频率与权限由你自己控制、数据在你自己的盘上（可再自行加密）。
3. **坚果云技术可行、但不该是主推后端。** 它**没有增量变更接口**，且单次返回上限
   750 条**必须分页否则「静默同步不完整」**（官方原文警告）。要做多设备可靠增量，
   Google Drive / OneDrive 的 `changes` / `delta` 才是正解。
4. **最大的工程风险不是存储后端，是「表格存储 → 文件存储」的语义改造。**
   现在是「每个会话一行、整行 LWW 覆盖」，文件存储必须改成「组级分片 + 乐观锁 +
   三方合并」。这是本方案 70% 的工作量。
5. **工作量和风险都超出「试用版」能承载的范围。** 我的建议是
   **先做「只读导入 + 单向备份」的最小可用版**（见 §7），把「双向实时同步」放 V2。
   理由在 §6，用一句话概括：**TapStack 的数据是「无回收站、删除即物理清除」的，
   双向文件同步一旦出错，代价是用户不可逆丢数据——这个风险不该由「试用版」承担。**

## 1. 你的原始需求与我的理解

你的原话拆成四条诉求：

| 诉求 | 我的理解 | 是否有更好的路径 |
|---|---|---|
| 自动同步带来麻烦，但想保留 | 保留「跨设备找回」这个能力，不想被我的后端绑住 | 方向对。但要区分「自动同步的**语义**」和「自动同步的**后端**」——见 §3 |
| 借鉴其他数据同步方式，让用户自行提供存储 | BYOK（Bring Your Own Key/Storage），Floccus 的路线 | 对。Floccus 是这条路最成熟的样本 |
| 不占我的存储空间、优化访问权限和频率 | 省掉 Supabase egress 配额与数据库成本 | 对。这是本次改动最实的收益 |
| 用户数据私密性更强 | 数据不在别人的服务器上 | 对，但注意：**放在「用户自己的云盘账号」≠「更私密」**，
云盘服务商仍能看到明文。真正的私密来自**客户端加密**，见 §5.2 |
| 把当前数据库表存储改为适合 Web3 存储的形式 | 表行 → 文件布局 | 这项是**大工程**，且「表→文件」的改造量常被低估，见 §4 |
| 尽可能提升用户实时体验 | 同步要快、要及时 | 与「文件后端」天然有张力，见 §6.2 |

**一条必须先说的判断**：你说的「自动同步带来了很多麻烦」，从仓库历史看，
最大的麻烦其实是 **Supabase egress 配额见底**（1.23.0 把自动同步默认关掉、
加四档间隔就是这个原因），以及 **LWW 合并模型下跨设备删除/编辑的静默丢失**
（1.22.16 / 1.22.17 连续几个版本在修）。**换存储后端并不能修掉合并语义的问题**，
它只是把问题从「服务端不可靠」搬到「文件并发不可靠」。§4 会说明为什么这一项
无论如何都要做。

## 2. 先纠正一个术语：「Web3 存储」与「自带存储」不是一回事

这是本方案最重要的一次澄清，因为**如果你按「Web3」去找方案，会找到一堆你用不了的
东西**，或者被「去中心化 = 更私密」的宣传误导。

| 方案 | 形态 | 你要自己运维吗 | 数据经过谁 | 对 TapStack 的适配 |
|---|---|---|---|---|
| **WebDAV / 云盘文件**（坚果云、Dropbox、Drive、OneDrive、S3/R2、自建 Nextcloud） | 一个目录 + 若干文件，扩展直接用 HTTP 读写 | **否** | 你自己选的云服务商 | ✅ **本方案采纳** |
| **IPFS / Arweave / Filecoin**（所谓 Web3 存储） | 内容寻址的文件，分布式网络 | **要么自己跑 IPFS 网关，要么用公共网关** | 公共网关 = 第三方节点 | ❌ 见下 |
| **Sia / Storj / 分布式存储矿网** | 分布式对象存储 | 租凭据 | 矿网节点 + 客户端加密才成立 | ❌ 生态不成熟 |

为什么 Web3 存储不适合 TapStack：

1. **「去中心化」的代价是你要么自建、要么更信任第三方。** 想不运维就得用公共网关；
   公共网关能看到请求内容的明文（除非你自己加密，见 §5.2——但那样网关只存密文，
   也就没必要用 IPFS 了，WebDAV + 客户端加密一样，而且网关是自己选的、可换的）。
2. **IPFS 网关的可用性由第三方决定**，而 TapStack 的定位是「跨设备找回工作现场」，
   找不回是产品级事故。你不能把数据可用性押在公共网关上。
3. **协议演进风险**：IPFS 的 CIDv1 / libp2p 升级、pin 服务的收费变化，都会变成
   你的维护负担。

**结论**：本方案全部使用「自带存储（BYOK）」这一表述，后端是一组具体可点的服务商
（坚果云、Dropbox、Drive、OneDrive、S3/R2、自建 WebDAV），不是「Web3 协议」。
你原话里的「Web3 存储」我理解为「WebDAV 这类文件型云存储」的意思——
**如果你的真实意图是去中心化协议本身，请告诉我，那是另一条（我不推荐的）路线。**

## 3. 现状：同步层已经是「可替换后端」的形状

好消息：**这不是从零开始。** 仓库在 1.22.x 的 S3 拆分里已经做好了端口抽象：

```
src/utils/supabase/ports.ts        ← 接口定义：SupabaseSyncPort（8 个方法）
src/services/tabGroupSyncService.ts ← 透传层：默认绑真实 sync，可 setSyncPort 注入替身
src/utils/supabase/sync.ts         ← Supabase 实现（upload/download/probe）
```

`tabGroupSyncService.ts` 顶部注释写着「S3：透传层依赖 `SupabaseSyncPort` 接口而非
具体实现……测试或未来多实现可经 `setSyncPort` 注入替身」——
**「未来多实现」这句话在写下时是空话，现在它有用武之地了。**

因此工程结构上：

- ✅ 引入第二个后端（BYOK）是**接进一个已有接缝**，不是重写整个同步层
- ⚠️ 但 `SupabaseSyncPort` 的 8 个方法签名**是按 Supabase 的能力设计的**
  （例如 `uploadTabGroups` 返回 `{ result, writtenTombstoneIds }`、
  `purgeExpiredCloudTombstones(maxAgeDays)` 依赖云端行）。文件后端要**重新设计
  这层接口**，而不是硬把文件操作塞进这些方法名里。

关键现状事实（本次实际读码确认，用于估算）：

| 事实 | 位置 | 对方案的影响 |
|---|---|---|
| 合并语义 = **组级 LWW 整组覆盖**（`lastOp = {deviceId, seq}` 全序决胜） | `src/core/opStampMerge.ts` | 好消息：OpStamp 是「设备无关的全局时钟」，**天然可搬到文件后端**，不需要改成向量时钟 |
| 删除即物理清除，跨设备删除靠云端行 `is_deleted` 标记（保留 30 天后物理清理） | `supabase/migrations/20260825130248_add_is_deleted_tombstone.sql` | **文件后端没有「行」可标记**。必须换一种删除广播载体，见 §4.2 |
| 增量上传水位按 `userId` 寻址 + 绑定 `deviceSeq` 防时钟回退 | `src/utils/supabase/syncWatermark.ts` | 水位键要换成「后端标识」寻址，逻辑可复用 |
| 全量下载前有「指纹探活」短路（只拉 `id, updated_at, version, is_deleted`） | `src/utils/supabase/probe.ts` | 文件后端可用 **ETag / Last-Modified / 文件清单**替代，且**更便宜**（一个 PROPFIND 拿全量指纹） |
| 分页下载用 offset + `created_at, id` 双排序（因 `created_at` 大量并列曾丢 25% 数据） | `src/utils/supabase/download.ts`、`.memory/pagination-requires-unique-sort-key` | 文件后端**天然没有分页问题**（一个 GET 拿全量）——这是改动的**收益**之一 |
| 加密：数据上云前用 PBKDF2(userId+deviceId, 100k) → AES-256-GCM 逐组加密 | `src/utils/encryptionUtils.ts` | 文件后端的加密方案要**重新设计**（用户没有 Supabase userId），见 §5.2 |
| `manifest.json` 的 CSP `connect-src` 只允许 `https://*.supabase.co` | `manifest.json:8` | 改后端必须放开 CSP 或动态加 host；且 `host_permissions` 要加，见 §5.1 |
| 自动同步已默认关闭 + 四档间隔 + 失败退避（1/2/5 分钟，封顶 8 次） | `src/background/backgroundSync.ts`、`syncBackoff.ts` | **调度骨架可以直接复用**，只改「到点了去哪儿同步」 |

## 4. 核心工程：表存储 → 文件存储的语义改造

这一节是整个方案的技术心脏，也是工作量的大头。

### 4.1 文件布局：为什么不能用「一个文件存全部」

直觉方案是「把全部 groups 序列化成一个 JSON 丢到云盘」。**不要这么做**，三个理由：

1. **每次改动都要重写整个文件。** 用户改一个会话的名字 ⇒ 上传全量。
   300 个会话的 JSON 假设 300KB，每次改名重传 300KB，在坚果云 600 次/30 分钟的
   免费额度下没问题，但**手机上流量和耗电、以及「实时体验」都直接受影响**。
2. **无冲突粒度。** 全文件覆盖时，两台设备同时改**不同**的会话也要互相冲突。
   Floccus 的 WebDAV 适配器就是这么做的（单文件 `bookmarks.xbel`），但它靠
   「先拉下来算 diff 再整体 PUT」绕开冲突，代价是每次同步都全量传输。
3. **删除熔断粒度太粗**（见 §4.4），误删保护很难做细。

**本方案采用「清单 + 分片」布局**（这是 Floccus 在 Nextcloud 后端上学到的，
但在文件后端上还没人做，TapStack 可以做在前面）：

```
{用户配置的目录}/
  manifest.json            ← 目录清单：版本、各分片的 ETag/大小/修改时间、加密元信息
  groups/
    <groupId前2位>/<groupId>.json    ← 每个会话一个文件，内含该组的 tabs 数组
  settings.json            ← 用户设置（单文件，LWW）
  .tapstack/
    base.json              ← 上次成功同步的「共同祖先」指纹快照（本地，不上传）
    journal.json           ← 待上传/待确认队列（本地，不上传）
```

设计要点：

- **每个会话一个文件** ⇒ 改一个会话只 PUT 一个文件，天然是「增量」。
- **`groups/` 按前两位分目录** ⇒ 避免单目录几万文件导致 PROPFIND 返回 750 条上限
  被打爆（坚果云官方限制，见 §1.7 of 调研报告）。
- **`manifest.json`** 是「探活」的廉价入口：只 GET 这一个小文件，比较里面的
  ETag 列表与本地记录的基线，就知道「远端有没有变」，**不需要 PROPFIND 全目录**。
  这是比 Supabase 的「指纹列查询」还便宜的一层。
- **`base.json` 存在本地、不上传** ⇒ 有了「共同祖先」才能做三方合并。

### 4.2 删除广播：无墓碑模型下的载体问题

现状：`is_deleted` 列 + 30 天 TTL 是「删除意图跨设备传播」的**唯一载体**。
本地物理删除后，如果上传失败，那些行仍是活跃行，对端合并时会把组整组加回来（复活）。

文件后端的等价物：**「组文件还存在但内容是墓碑」**（Floccus 早期墓碑模型，
后因与「删除即删除」的产品定义冲突被砍；TapStack 需要换个名字换个做法）：

```
groups/<id>.json 里写 {"t":"deleted","at":"<ISO>","by":"<deviceId>","seq":N}
```

- 对端读到墓碑 ⇒ 物理移除本地该组，并把它 id 登记进自己的 `journal.json`。
- **TTL 清理**：随上传执行「删除超过 30 天的墓碑文件」——与现在的
  `purgeExpiredCloudTombstones` 语义完全一致，逻辑可照搬。
- **新增风险**：墓碑文件与活跃文件的区分**完全依赖文件内容**。如果用户手动删了
  `groups/` 目录，所有设备都会认为「云端全空」⇒ 需要 §4.4 的熔断 + 「远端为空
  时拒绝覆盖本地」的硬防线。

### 4.3 并发控制：抄 xBrowserSync，不要抄 Floccus 的锁

调研结论（详见调研报告 §1.3 / §2.2）：

- **Floccus 的 `.lock` 是软锁**：两个客户端都能 PUT 成功，只是「大概率避免」并发，
  没有互斥保证。它靠「上次成功同步的快照 + 重新规划」在事后修正。
- **xBrowserSync 的乐观锁是真保证**：上传时带上「我上次看到的 `lastUpdated`」，
  不一致就 409，客户端重新拉取合并后重试。

文件后端天然支持后者（**WebDAV / S3 / Drive / OneDrive 都有 ETag**）：

```
PUT groups/<id>.json
Headers:
  If-Match: "<我上次 GET 时看到的 ETag>"     ← ETag 不匹配 → 412 → 我落后了
```

配合「分片粒度」，冲突面 = **单个会话**，而不是「整个库」。这就是分片的最大价值：
它把并发冲突从「全局」缩小到「一个会话」，而 TapStack 的产品语义本来就是
**组级 LWW 整组覆盖**（`opStampMerge.ts`）——**语义与分片粒度天然对齐**。

### 4.4 熔断：抄 Floccus 的删除熔断（当前项目缺的最后一道防线）

Floccus 的规则（`src/lib/strategies/Default.ts:996`）：

```
一次同步要删除的条目 > 总数 20%（且至少 5 条、上限 1000 条）→ 中止同步并报错
```

TapStack 现状**没有这道防线**。而文件后端引入了两条新的「静默清空」路径：

- 用户手动在云盘里清空/移动了 `groups/` 目录 ⇒ 远端读回「0 个组」
- manifest 损坏 / 分页只读到一半（坚果云 750 条上限忘了分页）⇒ 远端读回「少一半组」

这两条在当前 Supabase 模型下**不会**导致本地数据丢失（本地是 master），
但如果按「下载覆盖本地」的语义实现，就会直接清空用户本机的会话——
**在无回收站模型下不可逆**。

**因此：熔断是 BYOK 后端的 P0 前置，不是 P1 增强。** 具体设计见 §7.2 T2。

### 4.5 三方合并 vs 两路合并：保持现状，不在这一版动

Firefox Sync 的血泪史值得记住（调研报告 §3.1）：
- 早期「逐记录时间戳 LWW」→ iOS 做真三方合并（存共同父版本）→
  Desktop **退回两路合并**，Dogear 文档亲口承认「某些冲突会导致一侧改动被回滚，
  即数据丢失」。

TapStack 现状是**组级 LWW + OpStamp 全序决胜**，本身就是一种确定性的两路合并。
**本方案保持它不变**（理由在 §6.1）。新增的 `base.json`（共同祖先）在第一版
**只用于冲突检测与诊断**，不做三方合并——因为：

- TapStack 的 groups 是**扁平数组**（不像书签有深层文件夹树），冲突面小得多；
- 引入三方合并意味着「同一个会话里两台设备各加一个标签」也自动合并，
  这与 README 明写的产品语义「**整组覆盖：最后保存的一方为准**」冲突，
  属于**产品决策**，不能由我在工程方案里悄悄改。

## 5. 存储后端选型

调研报告 `.ai-logs/research-webdav-backends.md` 的对比（已验证事实为主）：

| 后端 | 增量变更 | CORS | 条件写（乐观锁） | 凭证形态 | 适配度 |
|---|---|---|---|---|---|
| **坚果云 WebDAV** | ❌ 无 changeToken | ❌ 不返 CORS 头（但扩展有 host 权限可用） | 推测支持（需实测） | HTTP Basic + 应用密码 | ⭐⭐⭐ 简单可靠，适合手动/低频 |
| **Dropbox API** | ✅ cursor + `has_more` | ✅ | ✅ | OAuth2 (PKCE) | ⭐⭐⭐⭐ |
| **Google Drive v3** | ✅ `changes` + pageToken | ✅ | ✅ ETag + If-Match | OAuth2 | ⭐⭐⭐⭐⭐ 增量最好 |
| **OneDrive / Graph** | ✅ `delta` link | ✅ `*` | ✅ eTag + If-Match | OAuth2 (MSAL) | ⭐⭐⭐⭐ |
| **S3 兼容 / Cloudflare R2** | ⚠️ 无 change feed（List + ETag 对比） | 需配（`ExposeHeaders: [ETag]`） | ✅ 原生 `If-Match`/`If-None-Match` | Secret（风险高） | ⭐⭐⭐ 技术用户 |
| **通用 WebDAV**（自建 Nextcloud 等） | ❌ | 取决服务器 | 取决服务器 | Basic/Bearer | ⭐⭐⭐ |

### 5.1 一个关键的 MV3 约束（真机实测结论）

调研 agent 用 Playwright + Chrome for Testing **真机加载两个 MV3 扩展做对照实验**：

```
A：声明 host_permissions: ["https://dav.jianguoyun.com/*"]
    GET / PROPFIND / OPTIONS → HTTP 401   ← 请求到达了服务器，只缺认证
B：不声明任何 host_permissions（负向对照）
    GET / PROPFIND / OPTIONS → ERR: Failed to fetch   ← 浏览器本地拦下，请求从未发出
```

结论：
- **坚果云不返回任何 CORS 头**（实测多 Origin 一致），
  但 MV3 扩展只要声明 `host_permissions`，Chrome 直接豁免 CORS。
- **所有请求必须在 background service worker / popup / options 里发**，
  content script 即使有 host 权限也仍受同源策略约束（Chrome 官方文档原文）。
  → TapStack 恰好所有同步代码都在 SW 侧（`syncEngine.ts` 在 SW 上下文运行），
  **架构上已经满足，无需改造**。
- `host_permissions` 写法要收窄：`https://dav.jianguoyun.com/*` 而不是 `*://*/*`
  （后者会拿「读取和更改您在所有网站上的数据」的安装警告）。
  但因为用户可能配任意自建地址，需要 `optional_host_permissions` + 运行时
  `chrome.permissions.request()`。

### 5.2 加密：这是「私密性」的唯一真身

你说「用户数据私密性更强」——**这一条必须说清楚，否则是假承诺**：

- 放在「用户自己的云盘账号」里 ≠ 更私密。**云盘服务商仍能看到你的明文**
  （坚果云、Dropbox、Google 都能技术上做到）。
- 真正的私密来自**客户端加密**：数据在离开浏览器前就用用户口令派生的密钥加密，
  云盘上只有密文。**此时云盘服务商看到的只是一堆乱码**——这才是「比我的服务器更私密」。

Floccus 与 xBrowserSync 的共同做法（可直接抄）：

```
PBKDF2-HMAC-SHA256(口令, 随机 salt, 250_000 轮) → AES-256-GCM
密文格式：base64( iv(16B) || ciphertext )
```

要点与陷阱：

- **salt 每次上传都随机生成** ⇒ 每次密文都不同 ⇒ **判「要不要上传」必须用
  明文哈希，不能用密文哈希**（这是 Floccus 踩过的坑，`Crypto.ts` + `onSyncComplete`）。
- WebCrypto **不支持 Argon2/scrypt**（MDN 算法表）。OWASP 基线是 Argon2id ≥19MiB，
  但在扩展里只能 PBKDF2；OWASP 对 FIPS 场景的 PBKDF2 基线是 ≥600k 轮。
  → **建议 250k（对齐 Floccus/xBrowserSync 的业界事实值），并在 UI 里说明「这是
  防离线明文，不是防运行时」**。
- 用户能不能每次输口令？**不能**（体验灾难）。折中：
  「设备密钥（高熵随机）加密密文 → 设备密钥用用户口令低轮数派生加密 → 存 storage.local」
  这套两层是 1Password 的做法，工程量大。**第一版建议：口令只在「首次配置」与
  「解锁」时输入，密钥派生结果缓存进 `storage.local`，并在 `onStartup` 时用
  设备密钥自动解密。**
- **`chrome.storage.local` 默认暴露给 content scripts**（Chrome 官方文档原文），
  必须显式 `chrome.storage.local.setAccessLevel({ accessLevel: 'TRUSTED_CONTEXTS' })`。
  当前 TapStack 没有 content script，所以这条是「防御性加固」，成本极低。
- **凭证类型选择**：OAuth（Drive/OneDrive/Dropbox）风险低于应用密码（坚果云）
  与 S3 Secret（最高）。**因此推荐顺序：Drive/OneDrive/Dropbox > 坚果云 > S3/R2。**

### 5.3 「同步实时体验」的现实约束

你说「尽可能提升用户的实时体验」。文件后端下的现实：

| 约束 | 事实 | 出处 |
|---|---|---|
| MV3 service worker 30 秒空闲 / **5 分钟单事件硬上限** | 超时 SW 直接消失，`finally` 不执行 | Chrome 官方 |
| 一次 4000 条书签的 WebDAV 全量同步实测 **~4 分钟** | Floccus 自己的基准数据 | Floccus README |
| Chrome alarms **最小 30 秒**（Chrome 120+），且 **unpacked 开发构建豁免 clamp** | 本地 15 秒跑得好好的，发布后变 30 秒 | Chrome 官方 |
| **创建同名 alarm 是覆盖，不是「仅当不存在才创建」** | 每次 SW 唤醒无条件 create ⇒ alarm 永远不触发 | Chrome 官方 |

⇒ **「实时」只能做到「秒级～分钟级」，做不到 Chrome bookmarks 那种「打开即同步」。**
TapStack 现状已经是「后台 alarm + 事件驱动上传」，所以**体验不会变差**，
但**也别指望变好**。分片设计让「改动一个小会话」的同步成本从「全量」降到「1 个 PUT」，
这已经是文件后端能做到的最好体验。

## 6. 两个必须你拍板的取舍

### 6.1 「整组覆盖」的已知代价，要不要在这次一并改掉

README 明写的产品语义：

> **整组覆盖**：同一会话在两台设备上被同时编辑时，以**最后保存的一方**为准
> （会话内标签的增删随整组一起同步，不逐标签合并）。错峰使用不受影响。

分片后这个代价**会更明显**（因为冲突粒度小了，用户更容易撞上）：
两台设备同时打开同一个会话，A 加一个标签、B 改个名字 → B 整组赢，A 加的标签没了，
且**无回收站、不可恢复**。

选项：

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. 保持现状**（我推荐 V1） | 组级 LWW 不变，只在 manifest/ETag 层面做冲突检测，检测到「同一组两端都改过」时**提示用户**「这个会话在两台设备上都被改了，以最后一次为准」 | 用户可能丢标签，但至少**知情** |
| **B. 改三方合并** | 引入 `base.json` 做真三方合并，同一会话内标签增删自动合并 | 与现有 README 产品语义冲突；属产品决策；工程量 +30% |
| **C. 改 CRDT**（如 Yjs） | 引入 Yjs 影子双写 | 1.22.11 刚删掉这套（5678 行），且当时判定为「过重」 |

**我的建议：V1 选 A**，并且**必须做「失败要出声」**——冲突发生时在 UI 里说清楚，
而不是静默覆盖。理由：这是个**产品语义**问题，不是技术问题。
而且 1.22.11 刚删 Yjs 是有明确判断的（`docs/slim-down-plan.md`），不该这么快翻案。

### 6.2 「试用版」到底该试用什么

你说「做一个试用版」。我认为**「WebDAV 双向实时同步」不是试用版能承载的**，
理由：

- 它改动的是**整个同步层**（接口重设计 + 语义改造 + 新后端实现 + UI 配置流程 + 迁移路径）。
  这不是「试用」，是「换一条主链路」。
- 失败代价是**用户不可逆丢数据**（无回收站模型）。试用版意味着用户量小、
  出事影响面小——但**代码缺陷不会因为用户量小而不存在**，反而因为缺乏真实用户
  反馈而更容易潜伏。
- 而「用户自行配置云服务」这个动作本身有**筛选效应**：愿意填 WebDAV 地址 +
  应用密码的用户，比点一下「登录」的用户少得多。这批人正是最需要反馈的那批人。

**我的建议（§7 给了完整分期）**：V1 先做「只读 + 单向备份」——
用户配好存储后，扩展能把数据**推上去**（备份，可换设备恢复），也能**从自己的存储里
拉回来初始化新设备**。**不做双向实时合并**。这样：

- 上行链路（分片 PUT + 加密 + 熔断）完整实现并被真实用户使用；
- 下行链路只有一个「首次导入」按钮，语义极简，不会覆盖用户数据；
- 双向合并留到 V2，等 V1 的上行数据在真实用户手里跑过一轮，确认分片布局、
  频率限制、加密口令体验都成立，再加下行合并。

## 7. 分期方案

### 7.1 V1（试用版）：单向备份 + 首次导入

**范围**（用户视角）：
1. 设置里新增「同步方式」：`TapStack 云端`（现有 Supabase） / `自带存储（试用）`
2. 配好后端：填地址 + 用户名 + 应用密码 + 加密口令 → **「测试连接」按钮**
   （明确告知会不会发请求、请求什么，不做静默探活）
3. **「备份到我的存储」** 按钮：手动上传全量分片到用户目录
4. **「从我的存储恢复」** 按钮：在空/新设备上把分片拉回来
5. 上行链路自带熔断与诚实报错

**明确不做**：双向实时同步、自动上传、跨设备合并。

**工程量**：中等。核心工作量在 §4.1 分片布局 + §5.2 加密 + §4.4 熔断 + UI。

### 7.2 V2：双向同步（等 V1 的数据在真实用户手里跑过一轮再上）

1. **上传**：本地 OpStamp 水位增量选组 → 只 PUT 变了会话的分片（`If-Match` 乐观锁）
2. **删除广播**：墓碑文件 + 30 天 TTL 清理（逻辑照搬 `purgeExpiredCloudTombstones`）
3. **下载**：先 GET `manifest.json` 探活 → 有变才按 ETag 差异拉受影响分片
4. **合并**：沿用 `mergeOpStamped`（组级 LWW），冲突时**出声提示**（§6.1 选项 A）
5. **调度**：复用 `backgroundSync.ts` 的 alarm + 四档间隔 + 退避状态机，
   只把「目标地址」从 Supabase 换成 BYOK 适配器
6. **熔断**（P0）：下载合并前先做「删除占比 > 20% 或绝对值 > N」检查，不通过就中止并报错

### 7.3 V3（可选，看 V2 的用户反馈再决定）

- 第三方云盘（Drive / OneDrive / Dropbox）OAuth 接入（真增量 API，工程量不小）
- 会话内标签级合并（真三方合并，需先改产品语义）

## 8. 迁移路径：现有 Supabase 用户怎么办

这是最容易被忽略、但**必须回答**的问题。用户明确说了「将原来的 Superbase 存储模式
改为 Web3 存储模式」——但**不能直接改掉**：

1. **现有用户的数据在 Supabase 里**。直接切换后端 = 直接看不到自己的数据
   （无回收站模型下不可逆）。
2. **两个后端不能同时自动写**（两份真相必然漂移）。

**建议路径**（需要你选）：

| 选项 | 做法 | 适合 |
|---|---|---|
| **A. 并存 + 一次性迁移向导**（推荐） | 设置里两种模式并存，用户手动点「从 TapStack 云端迁移到我的存储」，跑一次全量拉 + 上传，成功后提示可关闭云端 | 尊重用户选择，可回退 |
| **B. 新用户默认 BYOK，老用户保留 Supabase** | 不做迁移，只影响新装用户 | 工程量最小，但老用户的「麻烦」没解决 |
| **C. 硬切换** | 直接改后端，老用户看到空库 | ❌ **不建议，等于删用户数据** |

我的建议是 **A**。理由：这次改动的最大风险就是「用户看不到自己的数据」，
而**一次性的迁移向导正好是一次性把上行链路在真实数据量上验证的机会**。
（顺带解决 §7.1「上行链路缺乏真实数据验证」的问题——老用户的数据量比试用版用户大。）

## 9. 风险清单（按严重度）

| # | 风险 | 后果 | 缓解 |
|---|---|---|---|
| R1 | 下载合并时远端「看起来是空的」（目录被清 / 分页漏读） | **本地数据被清空，无回收站，不可逆** | 熔断（P0，§4.4）+ 「远端组数为 0 时拒绝覆盖本地」硬防线 + 熔断触发时**明确报错不出声假成功** |
| R2 | 跨设备删除靠墓碑文件，上传失败时对端复活 | 组复活（不是丢数据，但违反「删除即删除」） | 复用现有 `journal` / `pendingDeleteIds` 的 fail-closed 纪律（`storage.ts` 已有完整论证） |
| R3 | SW 5 分钟硬上限导致同步被腰斩 | 同步半途中断，状态不明 | V1 是单向上传，天然可重试（幂等 PUT）；V2 必须分批 + 断点续传或「小步快跑」 |
| R4 | 「Web3」实际被理解成去中心化协议 | 用户拿到的是一个不可靠的服务 | §2 已澄清；UI 文案不出现「Web3」字样 |
| R5 | 加密口令用户忘记 | 数据永久不可解 | UI 必须说清「口令无法找回」；提供「不加密」选项（诚实标注风险） |
| R6 | OAuth / 应用密码泄露 | 云盘被他人读取 | `setAccessLevel(TRUSTED_CONTEXTS)`；推荐 OAuth；最小 scope |
| R7 | 迁移失败（中途中断） | 用户数据在两个后端都不全 | 迁移向导必须幂等 + 可重跑 + 明确报告「哪一步没做完」 |
| R8 | `manifest.json` 与分片不一致（写入中途被 kill） | 探活误判 | 探活 miss 时走全量拉取（fail-safe 方向：多传不漏传） |
| R9 | 商店审核：新增 `host_permissions` | 审核问询 / 用户安装警告 | `optional_host_permissions` 运行时申请，收窄到具体主机；商店文案需说明 |
| R10 | 体积门禁 | `pnpm check:bundle` 超预算 `exit 1` | 现有体积门在 CI，`webdav` 库+加密代码要计入预算；必要时评估手写 fetch vs 引库 |
