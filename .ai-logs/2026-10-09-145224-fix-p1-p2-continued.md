## 二、执行过程

### 1. 架构 P0-1：migration_flags 被覆盖（数据丢失）

根因：`MIGRATION_SCAN_KEYS` 由 `Object.values(STORAGE_KEYS)` 全量派生，
**包含 migration_flags 自己**。于是搬运清单里出现这个键：

```
① 开头读 flags（KV 可能是空 → {}）
② 批量搬运 —— 把源里的 migration_flags 写进 KV（覆盖 ①）
③ 置位时若拿 ① 那个旧对象盖回去 → 源带来的其它标志被抹掉
```

丢掉的标志若是另一个迁移的完成标记，那个迁移就会**重新执行**，
把更旧的数据再覆盖一次，而 v1.22.0 起无回收站。

**两处都有**：`migrateFromLocalStorage` 与 `migrateFromChromeStorage`。

修法：`migration_flags` 不参与批量搬运，改三路合并
（① KV 现值 ② 源现值 ③ 本次置位）。

**第一版修复是错的**：我只做了「置位前重新读」，但批量写已经把 KV 原值覆盖了，
重新读读到的是被覆盖的那份。**是新加的测试把它抓出来的**（5→4 pass，
第二个用例红）。改成三路合并后才对。

## 三、遇到的问题（报错、阻塞、意外行为）

### 问题 1：我给 importFromOneTabFormat 加统计时造成**双重导入**

`apply_patch` 追加了 `const importedCount = await mergeImportedGroups(...)`，
却没删掉上面原有的 `await mergeImportedGroups(...)` —— 同一入口调两次，
而 `applyImportGroups` 每次新建 id、无去重 → **静默导入两份副本**。

**关键：30 个既有导入测试全绿** —— 它们只断言 `ok` / 失败原因，
不数导入后的组数，抓不住这个。靠我读 diff 自查发现。
随后专门加了源码计数回归锁（每个导入入口恰好 1 次调用），并做了变异验证
（加回重复调用 → 17/18 红 → 还原 18/18，sha256 一致）。

### 问题 2：变异 L 首次无效（变异根本没写入）

第一次变异 `saveSettings` 的 python 脚本 `s.index('    });')` 找不到就抛错退出，
文件**没被修改**，我却看到「20/20 全绿」——差点当成守卫生效。
这与第一批踩过的「基线就红导致对照无效」是同类陷阱。
重做时先 `print('确认写入: True')` 再跑测试，才拿到有效对照（19/20 红）。

### 问题 3：我差点把一个不可达路径当成 P0 报出来

UX 报告的 P2-2「保存时丢弃的危险 URL 不告知」，我顺着它往下查，
发现 `tabsToClose` 用 `filterValidTabs(原始tabs)` 而保存用 `sanitizeTabUrl`，
**判据可能不一致 → 标签被关闭但没保存**，一度以为是比 P2 严重的 P0。

用实际执行复核（9 个边界用例：无 url / 空格 / 畸形 / javascript: / chrome:// /
about:blank / https / loading:// / file://）：
**`droppedTabs > 0` 的用例数 = 0**。两道门判据同源（`sanitizeTabUrl` 内部就是
`isStorableTabUrl`），且 factory 只接受已过第一道门的 tab。
**判定：P2-2 不可达、非缺陷，我自己的担忧也不成立。** 记入误判，未改代码。

### 问题 4：模板字符串里的反引号提前终止字符串

（第一批已遇，本轮给 GRANT 注释加反引号时**又踩一次**）注释在模板字符串内部，
