# 2026-10-12 00:10 — 1.23.0 发布到 Chrome Web Store

## 对话出发点

Jasper：「你可以通过 Chrome 商店的 Skills 或 MCP，帮我把当前 build 好的包发布到 Chrome 商店。」

## 执行过程

### 0. 先读 skill + 项目脚本，不凭记忆

- 找到记忆里的 `~/.codex/memories/skills/chrome-extension-store-publish/SKILL.md`
  （那是为 `chrome-plugin-video-manager` 写的，用 `store-publish.mjs` + v2 API）。
- 本项目用的是**自己的** `scripts/cws-publish.mjs`（v1.1 API）。读了它的文件头注释确认
  能力边界与踩坑记录（v2 端点对本凭证 404、upload 必须 `curl -T`、空草稿 publish 是静默 no-op）。
- 没有 Supabase 式的 CWS MCP 工具可用，走 CLI。

### 1. 出包前拦截了一次「静默发错包」（SKILL.md 的头号红线）

仓库根目录已有 `chrome-extension.zip`，**但它内部 manifest 是 `1.22.16`**（2026-10-09 的旧包），
而当前版本是 1.23.0。若直接 upload，就会把**旧版**提交到商店 —— 这正是 SKILL.md 里
「`findLatestZip()` 不校验包内 manifest，会静默选错包直达生产」那条红线的现实版本。

⇒ 重新完整出包：`pnpm package`（= `pnpm build` + `package-extension.js`），
然后按 skill 的验证清单逐项核对 zip：

| 检查项 | 结果 |
|---|---|
| 包内 manifest version | `1.23.0` ✓（与 package.json 一致） |
| manifest 在 zip **根**目录 | ✓（非 `dist/` 嵌套） |
| `__MACOSX` / `dist/` 嵌套条目 | 0 ✓ |
| 1.23.0 > 线上版本 | ✓（线上 1.22.12） |

### 2. 查线上真实状态（权威来源 = API，不是仓库台账）

`cws-publish.mjs status` + v2 `fetchStatus`（v1.1 的 `PUBLISHED` projection 返回空，
v2 才是权威）→ **线上已发布 = 1.22.12（deployPercentage=100）**，
且**无任何待审版本**（`submittedItemRevisionStatus` 为空）。

### 3. 发现台账漂移（与本次发布无关，但必须据实修正）

`CHROMEWEBSTORE.md` 此前把 **1.22.13 / 1.22.14 / 1.22.15 / 1.22.16 都标成「待提审」**，
但实测：它们既不在线上，也没有待审记录 ⇒ **这几版实际从未上传过**。
（1.22.16 的文案里写着「数据库安全收口…现已启用」等，属于对用户的历史承诺，
但那版包从未到过用户手上。）

已据实改标为「未单独提审，随 1.23.0 一并上架」，并在文件顶部加了一条核对说明：
> 本表是**人工台账**，会漂移；判断线上真实版本必须用 `fetchStatus`，不要相信本表。

### 4. upload → 验证 crxVersion 变了 → publish

- `upload chrome-extension.zip` → `uploadState: SUCCESS`
- 按脚本红线，publish 前**先确认 crxVersion 已变**：`status` 显示 `crxVersion` 从
  `1.22.12` → **`1.23.0`** ⇒ 上传确实生效（不是空草稿）。
  注：同一响应里 `uploadState` 显示 `NOT_FOUND`，与 `crxVersion` 更新矛盾；
  我判断以 `crxVersion` 为准（它是上传结果的直接证据），并把这一步如实记录。
- `publish` → `{"status":["OK"],"statusDetail":["OK."]}`，exit 0

### 5. 独立验证（不信「命令返回成功」）

用 v2 `fetchStatus` 复核终态：

```
线上已发布: state=PUBLISHED, crxVersion=1.22.12, deployPercentage=100
待审:       state=PENDING_REVIEW, crxVersion=1.23.0   ← 本次提交
```

**待审状态与版本号都对**。线上仍是 1.22.12 属预期（过审后自动切换），
不是「没发成功」。

## 遇到的问题

1. **shell 把 URL 里的 `:fetchStatus` 吃掉了**：zsh 下 `$ITEM:fetchStatus` 被解析成
   参数展开，URL 变成 `.../items/tchStatus`（丢了 `:f`），返回 404。
   我一度以为是 v2 端点不可用（脚本头注释说「v2 对本凭证一律 404」），
   差点得出错误结论。改用 python `subprocess` 拼 URL 后正常返回 200。
   **教训**：zsh 里含 `:` 的 URL 变量要引号或走脚本，不要裸拼。
2. `db query` 式的 JSON 字段名假设（这里是 v1.1 的 `uploadState` 语义）与实证冲突时，
   以**能自证的字段**（`crxVersion` 变化）为准，并把矛盾如实记录，而不是挑一个顺眼的信。

### 遗留

- **审核结果需等待**（通常数小时到几天）。过审后线上会自动切到 1.23.0，
  届时可再跑 `fetchStatus` 确认 `deployPercentage=100`。
- 若被拒审：常见 `INCONSISTENT_LOCALE_METADATA` 不阻塞（见 skill），
  其它拒审原因需按邮件提示处理。
- 商店 listing 的**名称/描述/截图** API 改不了，仍需去 Developer Dashboard 手工对齐
  （本版无 listing 变更，故本次无需操作）。
- `scripts/cws-publish.mjs` 是 v1.1；**v1.1 于 2026-10-15 停支**，
  下次发版前需先迁移到 v2（v2 需要 `CWS_PUBLISHER_ID`，mcp.json 里已有）。
