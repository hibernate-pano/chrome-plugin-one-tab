## 3. 遇到的问题

### 3.1 测试抓到真问题：路径穿越（webdav/client.ts）

我写了断言「`../x` 不该逃出 base URL」，**它红了**。
根因：`encodeURIComponent('..')` **返回 `'..'`** —— 点号不在它编码的字符集里。
所以单靠编码拦不住路径穿越。

这不是理论风险：分片路径的一部分来自**远端 manifest.json**，
而那个文件在用户的云盘上（账号可改、可能被同步客户端弄坏）。
一个被改过的 manifest 就能让扩展读写配置目录之外的位置。

修法：显式拒绝 `.` 与 `..` 段（拒绝而非静默替换——静默改写会把明确错误
变成「数据写错地方」这种难查的故障）。

### 3.2 加密设计有性能缺陷（我自己审出来的）

subagent 交回的 `encryptJson(value, passphrase)` 每次调用都随机 salt、
都跑一遍 250k 轮 PBKDF2。单文件场景没问题，但我们是**分片**存储：

```
300 个会话 × 250k 轮 PBKDF2 ≈ 数分钟纯 CPU
```

直接撞 MV3 **单事件 5 分钟硬上限**（超时 SW 被杀，`finally` 都不执行），
而且全程占着单写者队列（用户此时点删除要排队）。
Supabase 侧 upload.ts 里那段「每组一次 PBKDF2-100k……300 组串行约 2.8s」
的注释就是同一类问题的历史记录。

修法：salt 作用域从「每文件」改为「整个库」（存 manifest，明文），
**IV 仍然每次随机**。新增 `Vault` 接口（`createVault` / `openVault`），
一次派生、多次加解密。

代价如实写进代码注释：攻击者爆破成本从「N 次 PBKDF2」降到「1 次」。
仍然选择这个取舍的理由：口令强度才是真防线，而「5 分钟跑完一轮同步」是硬预算。

### 3.3 一次假绿（我自己写的测试）

`webdavClient.test.ts` 里「412 必须可识别」那条**变异验证没抓到**。
根因：我只断言了 `status === 412` 与 `isPreconditionFailed`，
而删掉 412 专属分支后，通用 `!res.ok` 分支照样带着 status 412 抛错
（`isPreconditionFailed` 的默认值就是 `status === 412`）。

真正会丢的是一条**可据以行动**的信息：调用方看到 412 后必须
「重新拉取 → 合并 → 重试」，而不是当普通网络失败盲目重试。
收紧为断言文案含「其他设备修改」后，变异 1 红。

### 3.4 我自己的门禁假绿（命令层）

用 `pnpm type-check | tail -5 && git commit ...` 时，管道退出码取的是 `tail`，
所以 tsc 报错（`noUnusedLocals`）仍然走到了 commit。
**修法**：改用 `set -o pipefail` 并把 `exit=` 打出来自证。
同一条纪律适用于本仓库所有门禁命令。

### 3.5 环境坑：RTK 把崩溃的 linter 输出渲染成假报告

一次 `pnpm lint` 因 OOM 崩溃（`Linter process terminated abnormally`），
而输出被摘要成「**343 errors, 0 warnings in 9 files**」，还列出了
具体规则数与文件（全是 `dist/` 产物与根目录文件）。重跑 `exit=0`，无错。

**这是「假红」**——与假绿相反，但同样危险：会让人去查一堆不存在的 lint 错误。
**纪律**：崩溃的工具输出不能当报告读；先确认进程退出码，再读内容。

### 3.6 subagent 的一次自我更正（值得记录）

负责 crypto/failsafe 的 worker 报告：它前一轮的两个变异「误改到文件头注释里的
同款公式（未改到代码）」，红零条，它**如实标注并重做在代码行上**。

这正是变异验证要防的事：**变异必须真的改到代码**，改注释等于没变。
它自己发现并纠正，没有把「跑了一遍」当成「验证过了」。
