## 二、执行过程

### P1-4：新增 supportsOpStampStrict（只供删除链路）

**为什么不能直接改 supportsOpStamp()**：四条调用方里三条的 fail-open 退化
都是安全的（上传少带一列 / 下载退化 select('*') / digest 最小列集）。
只有删除广播是错的：「不知道有没有列」被翻译成「按没有来写墓碑」→
plain 墓碑不带 last_op_seq → 对端持平时判本地赢 → 删除被静默吞掉、之后复活。

专家已实测：直接让宽松版抛错 → 守卫绿但全量 fail 7，
正好打红 `downloadChain.test.ts:783`「宁可少选列，不可让整次下载失败」
（有意且正确）。所以分流：

- 新增 `supportsOpStampStrict()`（probe.ts）：
  确定性缺列（PGRST204 / last_op_seq）→ false（真没有，可走 plain，可缓存）
  非确定性失败（网络/权限/异常）→ **抛错**（不知道就拒绝执行）
  未配置 → 抛错；成功 → true（复用同一 cache）
- `upload.ts` 的 `markCloudGroupsAsDeleted` 改用 strict 版，
  另外三处（上传:364 / 下载 / digest）继续宽松版
- 抛错 → 本方法整体失败 → `pendingDeleteIds` 保留 → 下轮 alarm 重试
- `downloadChain + overwriteTombstone + offlineDeleteNoResurrect` 45/45 绿
  （证明第一版修法的问题没重演）
- 守卫：strict 版只能 1 处 `return false`（由 PGRST204 守卫）+
  删除广播必须调 strict + **另外三条必须继续宽松**（防一刀切回退）

### P2-5：SyncButton 覆盖确认读真值

`storage.getGroups()`（30s 缓存）→ `storage.getGroupsForWrite()`，
两处预览（上传/下载）都改。理由：这是**破坏性操作的确认闸门**，
用户核对数字后才按覆盖；通知是尽力而为，丢了通知+缓存未到期=陈旧数字。
执行侧本来就读真值，所以不会写错，但确认信息失真足以让用户做错决策。

## 三、遇到的问题（报错、阻塞、意外行为）

### 问题 1：守卫的函数体切片定位错了（类方法 vs 函数）

用 `indexOf('async function markCloudGroupsAsDeleted')` 切片，返回 -1，
随后 `slice(-1)` 拿到最后一个字符——断言对着空气运行，还**报红**。
`markCloudGroupsAsDeleted` 是**类方法**（`  async markCloudGroupsAsDeleted(`）。
修正后定位正确。这是「indexOf 返回 -1 必须先 assert」的纪律项。

### 问题 2：断言的正则按「有 await」写，但它在 Promise.all 里

`/await supportsOpStampStrict\(\)/` 匹配失败，因为实际写法是
`supportsOpStampStrict(),`（无 await）。输出 dump 显示函数体确实含它，
才发现是断言写错。改为按调用形态断言，并给负向断言加
`(?<!Strict)` 以免匹配到 strict 自身。

### 问题 3：我的守卫一度把真实调用误判成零命中（两轮）

轮 1：`migration_flags` 在调用处写成 `STORAGE_KEYS.MIGRATION_FLAGS`（常量引用），
我的正则只认字面量 `'migration_flags'` → 判成零命中。
轮 2：改成分辨常量后，`deviceId` 又被误判（STORAGE_KEYS 里根本没有 deviceId，
我的 fallback 逻辑把它和 MIGRATION 搞混了）。
两轮都是断言逻辑的错，不是产品代码的错。最终方案：
常量映射从 keys.ts **真实解析**，判定按「字面量或（值相等的常量引用）」。

### 问题 4：负向正则被历史注释误伤

`/export type ThemeStyle = ['"]legacy/` 匹配到了 tab.ts **注释里**
「原先这里是手抄联合类型 'legacy'」这句 —— 注释本身就是知识资产提旧写法。
给 describe 块加 `strip()` 先剥注释再断言（与 deadCodeGuards 同一条纪律）。

### 问题 5（重要）：变异 Q **失败了**，必须如实说明

把类型手工加成 `(typeof THEME_STYLES)[number] | 'neon'`（数组不加），
**tsc 不报错** —— 联合类型加成员本来就是合法 TS。
派生方案的防护是**单向**的：
- 给**数组**加成员 → 类型自动包含 ✅（危险方向已封）
- 给**类型**多加成员 → 数组不跟 ✅也不需要跟（类型变宽只会 accept 更多，
  不会让合法值被运行时判无效；反过来才会静默回落 legacy）

专家说的「编译期穷尽性保证」我**实际上没有完全做到**，但反方向本来就不危险。
已在测试里写了这段局限说明，不追求双向穷尽断言（维护成本高于它防的坑）。

### 问题 6：我就没做对的事情 —— 变异 R 是有效的

`VALID_THEME_STYLES` 改回手抄数组 → 18/19 红，还原 19/19。
危险方向（数组漏加）的防护是实的。
