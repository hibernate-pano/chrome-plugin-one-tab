## 追加四：真实执行验证迁移，抓出 5 个「只有连库才暴露」的缺陷（HEAD `fcfcce3`，14 提交）

门禁：**843/843 单测**、`pnpm validate` 通过。报告 `docs/deep-audit-2026-10-05-pm.md` 已同步。

### 为什么做这一轮
前两批写完迁移我只做了**静态检查**（单引号配对、定界符配对）就提交。这次起本地 **PostgreSQL 16.15**（`/opt/homebrew/opt/postgresql@16/bin`）真连库执行 —— **连续炸 5 次**，3 个在迁移、2 个在 verify 脚本，全部是静态检查与 `--dry-run` 放过的。

### 5 个坑（下次写 SQL 前必读）
1. **`REVOKE … FROM anon` 在角色不存在的库上直接 ERROR** → 单事务回滚 → 留下「函数建了但权限没收回」的半成品，**比不跑更危险**。必须 `DO $body$` + `pg_roles` 判存在性 + 动态 `EXECUTE`。⚠️ 历史迁移 `20260913132928` 有同样写法，Supabase 上角色恰好存在所以侥幸没暴露。
2. **`RAISE '…>%…'` 会把 `%>` 当成「> 加一个参数」** → `too few parameters`。文案里别用 `%` 紧跟符号。
3. **`unnest(ARRAY[…]) AS r` 后不能在同层 WHERE 用 `r.oid`** → `missing FROM-clause entry`。用 `FOREACH … IN ARRAY`。
4. **`pg_policy.polqual` 不是文本，是 `pg_node_tree`** —— `USING (true)` 存成 `{CONST :constvalue 1 […]}`。写 `polqual === 'true'` **永远不成立 ⇒ verify 漏检**（比报错危险得多：会让人以为已收口）。必须用 `pg_get_expr(pol.polqual, pol.polrelid)`。
5. **`ARRAY(SELECT rolname … WHERE r.oid = ANY(…))`** —— ARRAY(SELECT) 形式下没有 FROM 别名，必须写全限定名 `pg_roles.oid`。

### 方法论：漏检比报错危险
M4 是这轮最重要的发现。**报错会让人去查，漏检会让人以为已经收口。** 写任何「校验/断言」代码时，必须专门测一遍「**故意制造错误状态，确认它真的会报错**」——我这轮的 verify 脚本就是因为没做双向验证，漏检了整整一轮。

### 附带能力：本地验证迁移
`supabase-migrate.mjs` 原硬编码 `ssl:{rejectUnauthorized:false}`，连不上本地裸库（`server does not support SSL`）—— 而「执行前先本地验证」恰恰是最该做的事。加了 `SUPABASE_DB_SSL=false` 逃生开关（默认仍开启，生产行为不变）。用法：

### 写修复 SQL 时踩的 3 个坑（写 SQL 前必读）
1. **`pg_policy.polcmd` 对「带 WITH CHECK 的 UPDATE 策略」存的是 `'w'` 不是 `'u'`** ⇒ 按 `polcmd='u'` 判存在性会漏掉已有策略，`CREATE POLICY` 报 `already exists` 中断整个修复。**按名字判**。
2. **表级 GRANT UPDATE 会覆盖列级 REVOKE** —— 只写 `REVOKE UPDATE(plan) FROM authenticated` **无效**，因为表 ACL 还是 `authenticated=arwdDxt`（含 w），用户照样能改。**必须先 `REVOKE UPDATE ON profiles FROM authenticated`**。
3. RAISE 文案里 `%` 是占位符（已在迁移里踩过一次）。
